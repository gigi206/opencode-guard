# Configuration

## Configuration reference

All options live under `options` in the plugin entry.

| Option | Default | Description |
|---|---|---|
| `decision.baseURL` | — (required) | Versioned base URL, without the final path (e.g. `https://ai-gateway.example.com/v1`). Missing, empty or invalid: the decision model is disabled and only the local rules apply. Plain `http://` to a host that is not local (anything but `localhost`, `*.localhost`, `127.x.x.x` and `[::1]`) triggers a warning, since the key and the redacted tool calls would travel unencrypted; the model stays enabled. |
| `decision.protocol` | `"chat"` | `"chat"` for an OpenAI-compatible gateway, `"systemone"` for a direct System One API (see [Protocols](decision-model.md#protocols)). |
| `decision.model` | — (required) | Model name, e.g. `"nox-4b"`, or `"jev-latest"` for TypeSafe AI's Jev (experimental data level, hosted outside the EU). Missing or empty: the decision model is disabled. |
| `decision.apiKey` | — | Key sent as `Authorization: Bearer …`, normally a variable reference such as `"{env:NOX_API_KEY}"`. Absent or `null`: no authentication. Empty (referenced variable not set): the decision model is disabled. Never written to the log, and redacted like any known secret; a key shorter than 8 characters cannot be redacted verbatim, and a warning says so (also for short authentication headers in `decision.headers`). |
| `decision.timeoutMs` | `5000` | Timeout per call, from 100 to 60000. OpenCode applies no timeout to hooks, so this one is mandatory. A call that times out is retried once, so the wait can reach twice this value. |
| `decision.headers` | `{}` | Extra HTTP headers. Values are trimmed; a value containing a line break, or an invalid header name, is ignored with a warning. Every value of 8 characters or more is treated as a secret and redacted verbatim everywhere (outputs, requests, log), whatever the header's name, so a non-secret header (a title, an API version) is redacted too, and a file that contains its value can then no longer be rewritten (placeholder rule). |
| `askAs` | `"ask"` | `"deny"` (in any case) turns every confirmation request into a refusal (unattended mode, see [Confirmations and run modes](rules.md#confirmations-and-run-modes)). Typically `"{env:GUARD_ASK_AS}"`; empty means `"ask"`. |
| `thresholds` | see [Thresholds](decision-model.md#thresholds) | Decision thresholds. |
| `redactPrompt` | `true` | Redact secrets typed in the prompt. The redacted text is what gets stored. |
| `dangerousCommands`, `sensitiveFiles`, `decisionModel`, `scripts`, `redactOutputs`, `redactWire` | `true` | Turn a feature on or off; see [Turning features off](#turning-features-off). |
| `ruleOverrides` | `{}` | One built-in rule set by its identifier: `{ "<rule>": "off" \| "ask" \| "deny" \| "model" }`; see [Setting one rule](#setting-one-rule-ruleoverrides). `"off"`, `"ask"` and `"model"` apply only if your global configuration declares them too. |
| `exceptions` | `{}` | Files whose confirmation by a rule is not asked: `{ "<rule>": ["<absolute path>", …] }`, only `secret-file-read`; never a refusal; see [Exceptions for one file](#exceptions-for-one-file-exceptions). |
| `rememberConfirmations` | `0` (off) | Whole minutes, 1 to 60: a set of credential files you confirmed is not asked again in the same session during that delay; see [Remembering confirmations](#remembering-confirmations-rememberconfirmations). |
| `localAsks` | `"ask"` | `"model"` (in any case): the confirmations of the built-in rules without a setting are decided by the decision model; see [Letting the decision model decide local confirmations](#letting-the-decision-model-decide-local-confirmations-localasks). Applies only if your global configuration declares it too. |
| `selfProtectionByModel` | `false` | `true`: `localAsks: "model"` and `"model"` in `ruleOverrides` also reach the confirmations of the always-active rules (self-protection), except those about a change of the plugin's settings, a recognized launch of another OpenCode with its configuration or plugins changed or approving its own confirmations, and the OpenCode server API. Applies only if your global configuration declares it too. |
| `profile` | `"standard"` | `"credentials-only"` sets the default of `dangerousCommands`, `decisionModel` and `scripts` to `false`; see [Profile](#profile-profile). Applies only if your global configuration declares it too. |
| `agents` | `{}` | Settings for one agent: `{ "<agent>": { <policy settings> } }`; see [Settings by agent and by project](#settings-by-agent-and-by-project-guardjson). |
| `projects`, `trustedProjects` | none | Settings for a project directory, and the projects whose own settings may relax; read only from the global configuration file, the system configuration and the global `guard.json`. See [Settings by agent and by project](#settings-by-agent-and-by-project-guardjson). |
| `debug` | `false` | Also log allowed actions and redaction counts. Confirmations and refusals of tool calls, and the answers to them, are always logged, and so are the local confirmations decided by the decision model. |
| `logFile` | `$XDG_DATA_HOME/opencode/log/guard.log` | Plugin log file, falling back to `~/.local/share/opencode/log/guard.log`. `false` means stderr only. A leading `~` is expanded; a relative path triggers a warning. If the file cannot be created or written, the plugin switches once to the default log file and writes a warning there (the error code, never the system message), since the OpenCode service's stderr cannot be read. The log is never written through a symbolic link: a log file that is one, at startup or later, is treated the same way. A log file that is a credential file or a protected location (OpenCode's configuration, the plugin directory, startup files, `~/.ssh/`, git hooks, `/etc`) is refused at startup with a warning, and the default log file is used; so is a path with a symbolic link in any of its directories, or one that is not a regular file; the default path itself is always accepted. |
| `maxStateChars` | `4000` | Maximum size of the redacted input sent to the decision model, from 200 to 100000. Above 8000, a warning: the model is less accurate with a long state, and a state over its limit leads to a confirmation. |
| `cacheTtlMs` | `600000` | How long a verdict is cached (10 min), at most 3600000 (1 h). A verdict is reused only for the same tool, input, agent and directory, i.e. everything the model receives. Errors are never cached. Eviction is first-in, first-out. |
| `cacheMax` | `500` | Maximum number of cached verdicts, at most 10000. |
| `unprotectedAgent` | none | ID of an agent for which the plugin does nothing (no rules, no decision model, no redaction), selected with Shift+Tab; counts only in the global or system configuration; see [Unprotected agent](rules.md#unprotected-agent-unprotectedagent). Built-in agents (`build`, `plan`…) are refused. |
| `rules` | `[]` | Extra local rules, as an array: `{ "id", "pattern", "flags"?, "verdict": "deny" \| "ask", "reason", "tools"? }`. `tools` defaults to `["shell"]`; a single name such as `"*"` is also accepted. `"*"` matches every tool and is tested against the serialized input. OpenCode v1 tool names are mapped with a warning (`bash` → `shell`, `task` → `subagent`, `apply_patch` → `patch`), so a copied rule still applies; `todowrite` (present in v2 only when `experimental.todo` is enabled) and patterns that mention the renamed arguments `filePath` (now `path`) or `subagent_type` (now `agent`) are reported. The id `placeholder` is reserved for the built-in redaction placeholder rule: a rule given that id gets `custom-<index>` instead (its position in `rules`, counted from 0), with a warning. The top level of the global `guard.json` may hold more of them ([Your rules in the global guard.json](#settings-by-agent-and-by-project-guardjson)). |
| `secretPatterns` | `[]` | Extra secret patterns, as an array: `{ "type", "pattern" }` (regular expression source), or the pattern source alone (type `custom`). The type names the placeholder (`]` replaced by `_`, at most 200 characters). A named group `secret` (`badge_code=(?<secret>\S+)`) masks only its text, the rest of the match is kept; without it the whole match is masked. The pattern is compiled with the `g` flag only, so it is case-sensitive (JavaScript has no `(?i)`: write `[Ii]`). Your patterns run after the built-in formats: a value they already mask keeps their type. Unlike the built-in patterns, yours carry no guarantee of linear time: avoid nested repetitions such as `(a+)+`. An invalid pattern is reported at startup and ignored. `"enabled": false` keeps a pattern of yours aside (`enabled` other than `true` or `false` is reported and the entry ignored). Built-in formats are turned off with `redactionOff`, not here. |
| `redactionOff` | `[]` | Built-in redaction formats turned off, by name (`["jwt", "twilio_key"]`; `guard redaction` lists them): in the global or system configuration only, like the same key at the top level of the global `guard.json`, which `guard redaction off\|on <format>` writes ([Redaction formats](rules.md#redaction-formats)). An unknown name or one of OpenCode's own formats is reported and ignored. |
| `allowlist` | `[]` | Strings that are never redacted, compared exactly after trimming their surrounding spaces. A non-string entry is ignored with a warning (index and type only). A relaxation: each entry counts only if your global or system configuration lists it too, or in a project trusted at startup (see [Relaxations come from the global configuration](#relaxations-come-from-the-global-configuration)); otherwise it is ignored with a warning that gives their number, never their value. |
| `outputCheck` | on | `false` turns it off; `true` or `{ "enabled", "threshold", "timeoutMs", "skip", "questions", … }` (defaults: threshold 0.2, parts of 2000 characters, timeout 5000 ms per call; the other [settings and questions](decision-model.md#settings-and-questions-of-the-checks)) set it explicitly; settings other than `enabled` count only if your global (or system) configuration sets the same value, otherwise yours stay, or the defaults if you set none, with a warning: the decision model also looks for a secret written in plain words in tool outputs, and masks it; effective only if your global configuration file declares the same `decision.baseURL` and does not turn it off (an invalid value keeps it on, with a warning). See [Output check](decision-model.md#output-check-outputcheck). |
| `promptCheck` | on | `false` turns it off; `true` or `{ "enabled", "threshold", … }` (default threshold 0.2; the other [settings and questions](decision-model.md#settings-and-questions-of-the-checks)) set it explicitly; settings other than `enabled` count only if your global (or system) configuration sets the same value, otherwise yours stay, or the defaults if you set none, with a warning: the decision model also looks for a secret typed in plain words in your prompt, in any language, and masks it; effective only if your global configuration file declares the same `decision.baseURL` and does not turn it off (an invalid value keeps it on, with a warning). See [Prompt check](decision-model.md#prompt-check-promptcheck). |

Full example:

```jsonc
{
  "plugins": [
    {
      "package": "/path/to/plugin_opencode",
      "options": {
        "decision": {
          "baseURL": "https://ai-gateway.example.com/v1",
          "protocol": "chat",
          "model": "nox-4b",
          "apiKey": "{env:NOX_API_KEY}",
          "timeoutMs": 5000,
          "headers": {}
        },
        "thresholds": { "denyNoul": 0.9, "askNoul": 0.7, "denyRisk": 2.5, "askRisk": 1.5, "minConfidence": 0 },
        "askAs": "{env:GUARD_ASK_AS}",
        "redactPrompt": true,
        "debug": false,
        "logFile": "/path/to/guard.log",
        "rules": [
          { "id": "no-prod", "pattern": "--env=prod", "verdict": "deny", "reason": "production deployments are forbidden", "tools": ["shell"] }
        ],
        "secretPatterns": [{ "type": "internal", "pattern": "INT-[A-Z0-9]{24}" }],
        "allowlist": []
      }
    }
  ]
}
```

Numbers and booleans may also be given as strings (`"0.7"`, `"0,7"`; `"true"`/`"false"` in any case, `"1"`/`"0"`), as produced by `{env:…}`; an empty string means "not set". Invalid values fall back to their defaults, and unknown (e.g. misspelled) options are ignored; both are reported as warnings in the plugin log (never with the key's value, nor the content of an object). The model settings go under `decision`; `decisionModel` is only the on/off switch, and a warning says so if it receives an object.

## Protecting the plugin from project configuration

OpenCode applies a project's `opencode.json` (and `.opencode/opencode.json`) **after** the global one. A repository you open can therefore, without any action from the agent:

- remove the plugin: `"plugins": ["-guard"]` (by plugin id) or `"plugins": ["-*"]`. An entry with the path, `"-/path/to/plugin_opencode"`, has no effect;
- replace its options, by declaring the same `package` with its own `options` or none: OpenCode hands the plugin those instead of yours. The plugin reads yours back, so what you set stays and a project can only harden it: see [What a project keeps from your configuration](#what-a-project-keeps-from-your-configuration);
- block it with a policy: `"policies": [{ "action": "integration.use", "resource": "plugin:*", "effect": "deny" }]`.

The environment variables `OPENCODE_CONFIG` and `OPENCODE_CONFIG_CONTENT` can do the same for a process started with them; the agent cannot set them for a nested OpenCode without confirmation (see [Local rules](rules.md#local-rules)).

To check what applies in a given project, run `opencode plugin list` in its directory: `guard` must be listed.

**Minimum: a global policy.** Global policies outrank project ones. In the global `opencode.json`:

```jsonc
"policies": [
  { "action": "integration.use", "resource": "plugin:/path/to/plugin_opencode", "effect": "allow" }
]
```

This stops a project from blocking the plugin with a policy (with a project policy denying `plugin:*`, `opencode plugin list` still shows `guard`). It needs no restart and no duplicated setting, but removal (`"-guard"`) and replaced options remain possible.

**Full protection** needs a configuration layer loaded after the projects. Two ways, each with a cost:

- **System configuration** (requires root): `/etc/opencode/opencode.json` on Linux (`/Library/Application Support/opencode` on macOS, `%ProgramData%\opencode` on Windows) is loaded last and is not affected by `OPENCODE_CONFIG_DIR`. Declare the plugin there with its full options, plus the policy above. The file is owned by root: the agent cannot change it without `sudo`, which requires confirmation. The start line of the plugin log then ends with `system config: enforced`.
- **`OPENCODE_CONFIG_CONTENT` in the server environment** (stays in your home): `{"plugins": [<the full plugin entry>]}`, set with `opencode service set env` for the background service. The options are then duplicated, the variable's win, every change needs the variable regenerated and the service restarted (which interrupts sessions), and a `--standalone` process gets the protection only if the variable is also in its environment.

In either layer, also set `"experimental": { "location_idle_timeout": "60 minutes", "schedules": false, "artifacts": false }` (OpenCode's default; any other duration, or `false` to never unload): OpenCode reads this delay from the last configuration that sets it, so without it a project can shorten it and make the plugin forget sooner the scripts it saw written (see [Scripts written then run](operations.md#known-limitations) in the known limitations). OpenCode 2.2 reads `schedules` and `artifacts` from the same object: without them there, a project can turn on scheduled tasks (whose shell condition OpenCode runs itself, outside the tool hooks; the plugin refuses its confirmations rather than letting them pass) and artifacts (pages served by OpenCode's local server; the plugin judges the files written, and asks when their code calls the server API: see “The server API” under [Unprotected agent](rules.md#unprotected-agent-unprotectedagent)).

In both cases, **keep the entry in the global file too**, with the same options. OpenCode keeps the first plugin with a given id, in loading order. Without a global entry, a project could declare the same directory under another spelling (`/path/to/plugin_opencode/`, a symbolic link) with weaker options: loaded first, that variant would run and the later entry would be dropped as a duplicate. With the global entry loaded first, the later entry applies its options to it and the project variant is the one dropped. (For the system file, this follows from OpenCode's loading order; not verified.)

**Not covered by any of these:** a repository that ships its own plugin (`.opencode/plugins/`, or `plugins` pointing to a directory of the repository) runs code as soon as OpenCode opens it, which no plugin can prevent. Only open repositories you trust.

## Turning features off

Each feature has a boolean option, `true` by default (same style as `redactPrompt`). Set it to `false` in the plugin options:

| Option | What `false` turns off |
|---|---|
| `dangerousCommands` | Built-in local rules for dangerous actions: deletions (`rm`, `find -delete`, home directory moves), destructive git commands, devices and disk formatting, `sudo` and permission changes, `kill`, shutdown, `crontab`, installs and publishing, containers and infrastructure, downloaded scripts that are run, `eval`, dynamic execution through launchers (`xargs`, GNU `parallel`), interpreters and `awk`, shell startup files and `git` settings that name a program to run, running a file created by the agent that can no longer be checked, uploads and remote copies, network access by inline interpreter code, writes to startup files, `~/.ssh/`, git hooks and `/etc` (also as a path argument of an MCP or plugin tool; a write in a form the rules do not read is under [Known limitations](operations.md#known-limitations)), and CodeMode network access. Also in the shell sub-commands checked at permission time. |
| `sensitiveFiles` | Built-in local rules for credential files and outgoing secrets (including the reading of file headers to recognize private keys): reading a credential file (also as a path argument of an MCP or plugin tool), a credential file or a secret in a network command or in a command whose inline interpreter code makes network requests, an environment dump sent over the network, a secret in a web request, a search, MCP arguments or CodeMode code, reading a document the plugin cannot see inside. |
| `decisionModel` | Calls to the decision model; the `decision` settings are kept. Same as removing `decision.baseURL`. |
| `scripts` | Checks of [scripts written then run](decision-model.md#decision-model). |
| `redactOutputs` | Redaction of tool results and errors at the source: secrets are then stored in the history and shown in the interface. |
| `redactPrompt` | Redaction of the typed prompt. |
| `redactWire` | The safety net on model requests (HTTP bodies, WebSocket frames). |

Turning the local rules off does not mean "allow everything": with the decision model enabled, every action it does not stop runs, but it is still judged. The model alone would allow many of the actions the local rules send to confirmation (see [Decision model](decision-model.md#decision-model)). With both rule options and the decision model off, only the protections below remain.

**Always on, whatever the options:** the placeholder rule (writing a placeholder would destroy the real secret); self-protection: confirmation for writes to OpenCode's configuration (global, system, project `opencode.json`/`opencode.jsonc` and `.opencode/`, and any `opencode.json`, `opencode.jsonc` or `guard.json` wherever it is), to OpenCode's service file and to the plugin directory, for a shell command that names one of them without only reading, even if it does not write there, and for an MCP or plugin tool whose path arguments designate them, and for commands that start another OpenCode, change its service, print its password, environment or credentials, write a copy of its memory, request a pairing code, add or remove a plugin or an MCP server, or call its server API other than a known read, or use an OpenCode subcommand unknown to the plugin, and for a command whose program is known only when it runs (a command substitution joined to other characters in the command word, unless the word starts with it and a `/` follows it) or could not be determined (a command word longer than 1,024 characters that contains a quote, a backquote, `$` or a backslash, a command too complex to read, or an internal error of the analysis) (rules `self-protection`, `nested-opencode`, `opencode-service`, `opencode-server-api`), so that the agent cannot turn the other protections off without asking; your own `rules`; redaction of everything sent to the decision model and of the log; `askAs`.

To change a single rule rather than a whole group, see [Setting one rule](#setting-one-rule-ruleoverrides); to keep only the credential protections, see [Profile](#profile-profile).

Each option in force at `false` is listed in the log at startup (`INFO active (…; disabled: …)`) with a warning. From a project's `opencode.json`, such a `false` is a relaxation: it is ignored, with a warning at startup that names the option and gives the command for that project's directory, unless your global sources set it too (see [Relaxations come from the global configuration](#relaxations-come-from-the-global-configuration)); a `true` counts. For a repository full of fake test secrets, turn the option off for that directory only:

```jsonc
// ~/.config/opencode/guard.json (`guard set redactOutputs false --project /home/me/fixtures` writes it)
{ "projects": { "/home/me/fixtures": { "redactOutputs": false } } }
```

A repository you clone cannot turn a protection off this way, but it can still remove the plugin (see [Protecting the plugin from project configuration](#protecting-the-plugin-from-project-configuration)).

## Setting one rule (`ruleOverrides`)

`ruleOverrides` maps the identifier of a built-in rule, as listed in [Rule identifiers](rules.md#rule-identifiers), to a setting (in any case):

| Setting | Effect |
|---|---|
| `"off"` | The rule no longer asks or refuses: the call is judged as if it did not exist, by the other rules, then by the decision model if it is on. |
| `"ask"` | A refusal by this rule becomes a confirmation, and every confirmation by this rule stays with you: the decision model never decides it in your place, also where it would otherwise decide (heredoc data, CodeMode code). |
| `"deny"` | A confirmation by this rule becomes a refusal, also where the decision model would otherwise decide (heredoc data, CodeMode code) and in a script written then run, where the rules read its content and otherwise only ask (a non-shell script the model saw in full is left to the model). Its refusals are unchanged. |
| `"model"` | A confirmation by this rule is decided by the decision model, as described in [Letting the decision model decide local confirmations](#letting-the-decision-model-decide-local-confirmations-localasks). Its refusals are unchanged. |

```jsonc
"ruleOverrides": { "git-reset-hard": "off", "secret-file-network": "ask", "privilege": "deny", "eval": "model" }
```

- A setting on a rule wins over its group switch: `"ask"`, `"deny"` or `"model"` turns the rule on even with `dangerousCommands: false` or `sensitiveFiles: false`, and `"off"` turns it off in an active group. It also wins over `localAsks`: a rule set to `"ask"` keeps asking you when `localAsks` is `"model"`.
- The always-active rules (`placeholder`, `self-protection`, `nested-opencode`, `opencode-service`, `opencode-server-api`, `guard-cli`) accept only `"deny"`, and `"model"` when `selfProtectionByModel` is retained (never for `guard-cli` or `opencode-server-api`, nor for `placeholder`, which only refuses): `"off"` and `"ask"` are ignored with a warning, and so is `"model"` without `selfProtectionByModel`. `internal-error` and the identifiers of your own `rules` cannot be set (a user rule that reuses a built-in identifier makes it unsettable). An unknown identifier or an invalid value is ignored with a warning.
- `opaque-image` is off by default, whatever `sensitiveFiles` says: `"ask"`, `"deny"` or `"model"` turns it on, also from a project that is not trusted, since that only hardens. Set in the plugin options of your global `opencode.json`, it falls with them when a project replaces these options, and the rule goes back to off without a warning; `guard rules ask opaque-image` writes the global `guard.json`, which has no such weakness. On `opaque-document` and `opaque-image`, `"model"` is kept with a warning and asks like `"ask"`: the decision model would get only the file's name, and `localAsks` does not reach them either.
- Each setting applies to every finding of its rule before the findings of a call are combined: a rule set to `"off"` or `"ask"` never takes the place of another rule's refusal or confirmation, whether in the command, its other readings, the scripts it runs or the shell sub-commands OpenCode checks at permission time. A rule turned off can leave a weaker rule in place: with `"rm-critical": "off"`, `rm -rf ~` still asks under `rm`.
- The retained settings are listed in the start line of the log (`rule overrides: git-reset-hard off, …`).

## Exceptions for one file (`exceptions`)

`exceptions` lists, for a rule, the files whose confirmation you no longer want to give:

```jsonc
"exceptions": { "secret-file-read": ["/home/me/work/app/.env", "/home/me/.pgpass"] }
```

- **Rules.** Only `secret-file-read` accepts exceptions: its findings name the files they are about. Any other identifier (an always-active rule, `internal-error`, one of your `rules`, another built-in rule, an unknown one) is ignored with a warning.
- **Paths.** Each path must be absolute, since only an absolute path names one file for certain (a `~/…` or relative path depends on the `HOME` and directory of the shell, which the plugin does not see); it is replaced by its real path (symbolic links resolved) when the settings are read. A relative or missing path, or one with a `..` component, is ignored with a warning. `guard rules off secret-file-read --path <file>` writes one ([The `guard` command](#the-guard-command)).
- **Every file of the finding.** A confirmation is lifted only when every credential file the command or tool names, compared by real path, is excepted for the rule; a command that reads an excepted file and another one still asks, and the reason names both (at most three, then how many more).
- **Files known for certain only.** No exception applies when the file opened may differ from the one the plugin sees: a path that is not absolute, for the shell as for the tools, a home-relative one (`~/…`, `$HOME/…`) included, since the `HOME` of a shell command comes from the session's environment, which the plugin does not see; a path with a `..` component (the kernel resolves it after the links before it), a variable or a pattern in its name (or a `glob` or `grep` pattern), a missing file, a name inside a larger quoted word or next to a construction the plugin does not read word by word (heredoc, comment, backquote, substitution inside double quotes), a check stopped by a limit.
- **A command that only reads.** In a shell command, an exception applies only when every part of the command, the one that names the file included (parts chained before or after, a pipeline, a background job, a subshell, and every command or process substitution, those among the arguments of the part that reads included), is one of these programs, named alone (unquoted, not by its path), which modify no file, launch no other program and run no code whatever their options: `cat`, `head`, `tail`, `wc`, `grep`, `cut`, `tr`, `nl`, `tac`, `rev`, `fold`, `paste`, `base64`, `od`, `basename`, `dirname`, `realpath`, `readlink`, `pwd`, `ls`, `stat`, `echo`, `true`, `false`, `sleep`, `sha1sum`, `sha256sum`, `sha512sum`, `md5sum`, `cksum`, `cmp`, `uname`, `whoami`, `id`, each without a redirection to a file (`/dev/null` and descriptor duplications aside), and with no assignment. With any other program, even one that only reads the file, no exception applies: a database client or a tool that runs commands is not in this list, nor a wrapper (`sudo`, `env`, `timeout`…), a shell or an interpreter, nor `diff` (an option sends its output through another program). Otherwise a part that replaced a link or a directory on the path before the read would make the command read another file than the one checked. The other shell sub-commands OpenCode checks for the same call are held to the same rule. For reads you repeat with a program outside the list, `"model"` for `secret-file-read` in [`ruleOverrides`](#setting-one-rule-ruleoverrides) (for one project, in its `projects` section) lets the decision model decide that rule's confirmations instead of you.
- **A path to a regular file.** A name alone (`.env`) or a relative path (`./.env`) never matches an exception, for the shell as for the tools: a program may look it up somewhere else, and the plugin knows the command's directory only from its text. A listed path that is not a regular file once its links are resolved (a directory, a device) is ignored with a warning. An exception is about the local file a path names: a program that reads the same path somewhere else (on another machine, or from a directory it chooses) still benefits from it. It follows the path, not the file: a previous call, or a job left running in the background, that puts another file at that path is not seen, and reading the path then reads that other file without a question.
- **Never a refusal, never another rule.** An exception only lifts a confirmation of its rule, after `ruleOverrides`: with `"secret-file-read": "deny"`, reading the file is still refused. The other rules still apply to the same command (sending the file over the network is still refused by `secret-file-network`, a write to a protected location still asks). Once the file no longer counts, the decision model, if it is on, judges the call as one no local rule matches. A shell command run by OpenCode itself rather than by a tool call (the condition of a scheduled task) never benefits from it: its confirmation is refused. Nor does a script written in the session and run by a command, nor a call made by CodeMode code (a tool it calls, shell sub-commands included): their confirmations are still asked. The plugin recognizes such a call while it tracks the running code: from the start of the `execute` call until it ends or is not run (refused, not confirmed), however long it runs, for at most 10,000 code calls at once (beyond that, the oldest is forgotten), and not across a reload of the plugin, after which the call is treated as a direct one. An `execute` call that OpenCode itself stops after the plugin let it through (its own permission check, another plugin) stays tracked until it is forgotten that way: its identifier keeps asking.
- **Redaction unchanged.** Secrets read from an excepted file are still redacted in the tool output.
- **Where it may be set.** Like the other relaxations: the global configuration file, the system configuration, the global `guard.json`, their `projects` sections, the `guard.json` of a [trusted project](#settings-by-agent-and-by-project-guardjson), or the effective plugin options when a global source lists the same rule and real path; outside a project trusted at startup, an effective option's path is consulted only when a global source lists it as written. Elsewhere, and in any `agents` section, it is ignored with a warning naming the entry; the paths of a project `guard.json` that is not trusted are not consulted (the warning names them as written). The lists of every source and section that apply add up.
- **Log.** A call whose confirmation an exception lifted is logged at the info level with the rule and the file (`shell → lifted (exception, rule secret-file-read): /home/me/work/app/.env`). The start line and the line of a `guard.json` re-read give the number of exceptions retained (`exceptions: 2`).

## Remembering confirmations (`rememberConfirmations`)

Off by default. With `"rememberConfirmations": 10` (whole minutes, 1 to 60; `0` turns it off; any other value is ignored with a warning and leaves it off), once you confirm a `secret-file-read` request in a session, the same rule on exactly the same set of files (compared by real path) is not asked again in that session until the delay has passed since your confirmation (a use never extends it).

- **Risk.** During the delay, a new command on the same file passes without a question, whatever it extracts from it.
- **Only your confirmation is remembered**: not an allow by the decision model, not a refusal, not a request you did not grant, not a request set when OpenCode checks the shell sub-commands (the plugin does not see your answer there), and never a request whose files are not all known for certain (same cases as for [exceptions](#exceptions-for-one-file-exceptions)) or that an internal error accompanies. Another session, another set of files (one more or one less) or another rule asks again.
- **Delay in force when used**: removed or set to `0` (a `guard.json` re-read for instance), nothing is lifted any more. Like an exception, it never lifts a refusal, the other rules still apply, redaction is unchanged, and the decision model, if it is on, judges the call as one no local rule matches.
- **Where it may be set**: the same sources as `exceptions` (never an `agents` section); a value other than `0` is a relaxation. `guard set rememberConfirmations <minutes>` writes it. A shell command run by OpenCode itself rather than by a tool call never benefits from it. Nor does a script written in the session and run by a command, nor a call made by CodeMode code (recognized as above), and a confirmation given there is not remembered.
- **Log.** A lifted request is logged at the info level (`shell → lifted (remembered, rule secret-file-read): …`); the start line and the line of a `guard.json` re-read show `confirmations remembered for 10 min`.

## Letting the decision model decide local confirmations (`localAsks`)

By default, a confirmation asked by a local rule stays with you: the decision model only adds its opinion to the reason. With `"localAsks": "model"`, the confirmations of every built-in rule without a setting are decided by the decision model instead; `"model"` in `ruleOverrides` does the same for one rule. The setting of a rule wins: with `"localAsks": "model"`, a rule set to `"ask"` still asks you, and one set to `"deny"` refuses.

- **The model decides only when it judged the whole input.** It then allows, asks you or refuses, like for an action that no local rule matches, and the reason says so (`privilege escalation, left to the decision model by localAsks, decided by nox-4b: risk 0.10/3, …`). If the model is disabled or unreachable, if its answer is invalid, or if the input was cut to `maxStateChars`, the confirmation stays with you.
- **Refusals never change**: a refusal by a local rule stays a refusal, and `"model"` on a rule only reaches its confirmations.
- **Only the model of your global configuration allows**: the decision model allows a confirmation only if its address, model name and the other settings its verdict depends on (`decision.protocol`, `timeoutMs`, `apiKey`, `headers`, `maxStateChars`, `secretPatterns`, `thresholds`) are those your global configuration file or the system configuration declares for this plugin, and the system configuration when it declares the plugin, or else the global sources, switch it on, or in a trusted project; otherwise it may refuse, but the confirmation stays with you, with a startup warning (see [Decision model](decision-model.md)). The same holds for the two built-in exceptions, heredoc data and CodeMode's `fetch`.
- **A confirmation you must give always comes first.** When a call has several findings, a refusal wins, then a confirmation that stays with you, then one the model decides: one rule left to the model never hides another rule's confirmation, nor one found in another reading of the command, in a script it runs, or in the shell sub-commands OpenCode checks at permission time.
- **Never left to the model**, whatever the setting: an internal error (`internal-error`); a confirmation born from a check the plugin could not finish (a limit on what it reads, a command word whose program is known only when the command runs or cannot be determined, an OpenCode command line it cannot read, a command too complex to read, a write target relative to the launch directory or known only when the command runs); a refusal found only inside heredoc data or code given to an interpreter, which becomes a confirmation; a script written then run by the command; your own `rules`; and the read-only tools and the task list (`read`, `glob`, `grep`, `todowrite`), for which the model is never consulted. The rules about dynamic execution (`eval`, `xargs-dynamic-exec`, `parallel-dynamic-exec`, `dynamic-shell-source`, `git-config-alias`…) are ordinary rules: their confirmations are left to the model like the others.
- **Self-protection** (the always-active rules) stays with you unless `"selfProtectionByModel": true` is set as well; the `placeholder` rule only refuses and is not affected (`"model"` on it is ignored with a warning). What changes the plugin's settings is never left to the decision model, even then: running the [`guard` command](#the-guard-command) (`guard-cli`), writing a `guard.json`, an `opencode.json` or an `opencode.jsonc` (recognized by their names wherever they are, also under a directory known only once the shell expands it), an OpenCode configuration directory itself, its `plugin` or `plugins` directory (code OpenCode loads), the plugin directory or OpenCode's service file (`service.json`, `service-<channel>.json` and their backup copies under the service directories, which hold the service's environment and settings), with a tool or a shell command, a link to them included, a shell command that has one of them as a literal word and does more than read, even without writing there, and a write to an OpenCode location whose links could not all be followed (it may lead to them), `opencode plugin add`/`remove` or `opencode mcp add`, and `opencode service set`/`unset`. Nor, by your decision, a launch of another OpenCode that the plugin recognizes (`opencode run`, `serve`, `web`, `acp` or `attach`, or with `--auto`; `opencode` alone, without a subcommand, is recognized only with `--auto` or its hidden aliases, see [Local rules](rules.md#local-rules)) with an option that approves its own confirmations (`--auto`, `--yolo`, `--dangerously-skip-permissions`) or with a variable that changes its configuration or plugins (`OPENCODE_CONFIG`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CLI_CONFIG_CONTENT`, `OPENCODE_CONFIG_PROJECT_DISABLE`, `OPENCODE_DISABLE_PROJECT_CONFIG`, or `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `HOME`, from which its global configuration and its npm plugins are found), and a call to the OpenCode server API (rule `opencode-server-api`: the routes and `opencode api` calls described in [The server API](rules.md#unprotected-agent-unprotectedagent), `opencode auth export` and `opencode debug heap-dump`, which call it; not a known read, nor a call to another local service). The rest of self-protection (agents, commands, skills… in a configuration directory, another OpenCode launched without these options and variables, OpenCode's other service subcommands) can be left to it.
- **Shell sub-commands**: once the model has allowed a command on its whole input, the confirmations that a setting leaves to the model are not asked again for the sub-commands OpenCode checks at permission time; any other confirmation, a refusal, or another call still applies.
- **Unattended mode** (`askAs: "deny"`): a confirmation the model leaves to you, or that stays with you, is refused as before.
- **Log**: a local confirmation decided by the model is logged at the info level with its rule and the model's verdict (`shell → allow (model, rule privilege): …`). The start line shows `local asks: model` and `self-protection by model` when retained; if the decision model is disabled, a startup warning says these settings do nothing and the confirmations stay with you.

**Risk.** The decision model reads the command, including its comments, strings and heredoc bodies, written by the agent: text placed there can steer its answer. A confirmation left to the model therefore protects less than one you give yourself. Keep `"model"` for rules whose confirmations you find repetitive and low in risk, and leave self-protection and credential files with you.

## Profile (`profile`)

`"standard"` (default) or `"credentials-only"`. The latter sets the default of `dangerousCommands`, `decisionModel` and `scripts` to `false`: the credential file and outgoing secret rules, redaction, self-protection and your own `rules` remain. An option given explicitly wins (`"profile": "credentials-only", "dangerousCommands": true` keeps the rules for dangerous actions). An invalid value gives a warning and `"standard"`. The start line of the log then shows `profile: credentials-only`.

## Relaxations come from the global configuration

A project's `opencode.json` can replace the plugin's options (see [Protecting the plugin from project configuration](#protecting-the-plugin-from-project-configuration)). A rule set to `"off"`, `"ask"` or `"model"`, `"localAsks": "model"`, `"selfProtectionByModel": true`, the `credentials-only` profile, each entry of `exceptions` and of `allowlist` (a value never redacted is also no longer recognized by the rules on secrets, and the decision model and the log see it) a `rememberConfirmations` delay, `unprotectedAgent` and a switch at `false` (`dangerousCommands`, `sensitiveFiles`, `decisionModel`, `scripts`, `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck`, `promptCheck`) are therefore applied only if your global configuration file (`$OPENCODE_CONFIG_DIR`, or `$XDG_CONFIG_HOME/opencode`, or `~/.config/opencode`, as OpenCode resolves it, `opencode.json` or `opencode.jsonc`) or the system configuration declares this plugin with the same value for that entry (for `rememberConfirmations`, a delay at least as long). Otherwise each one is ignored with a warning that names the entry and says why (file missing or unreadable, not valid JSON, plugin not declared, value not set there). If these files cannot be checked at all, every relaxation is ignored, never applied. `{env:…}` references in them are resolved with the server's environment, as OpenCode does; for this comparison, a `{file:…}` reference is not followed, so its value does not match. They are read once, at startup. In a [trusted project](#settings-by-agent-and-by-project-guardjson), these relaxations are kept without that check (for `exceptions` and `allowlist`, the trust read at startup: a project untrusted while OpenCode runs keeps them until the next start), except `unprotectedAgent`, `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck` and `promptCheck`, never kept from a project: for those, a matching `projects` section of a global source declares the value too. The decision model follows the same rule: it allows a confirmation only with the address, model and other settings your global or system configuration declares (see [Letting the decision model decide local confirmations](#letting-the-decision-model-decide-local-confirmations-localasks)).

`"deny"` and a switch at `true` are accepted from any configuration. A feature switch you turned off stays off in a project that leaves it out; the project turns it back on by writing `true`. `outputCheck` and `promptCheck` are different: a check your global file turns off stays inactive whatever a project sets, as [its activation](decision-model.md#output-check-outputcheck) reads that file.

### What a project keeps from your configuration

OpenCode hands the plugin the options of one entry, whole: a project's entry, even without options, replaces yours. The plugin therefore reads back the entry of your global configuration file, or that of the system configuration when it declares the plugin (nothing replaces that one, so a key set only in the global file then counts neither with nor without a project). It reads them as OpenCode does: `opencode.json`, then `opencode.jsonc`, and the last entry of the plugin wins, a text entry without options included; `"-guard"` or `"-*"` after it means the file no longer declares the plugin. An entry is recognized by its absolute path or by the exact specifier the plugin was installed from: written as `file://…` or `./…`, or under the older `plugin` key, or as another revision, it does not count as a declaration. When no global source declares the plugin, a project's options apply as they are, under the rules above. A file that is not valid JSONC counts for nothing, as in OpenCode. When no entry is found and a file exists but cannot be read or parsed, or when an entry cannot be read back, the log says `settings of the global configuration not kept`, and the options handed by OpenCode apply under the same rules.

**A key the project leaves out keeps your value**, for every option. `agents`, `projects` and `trustedProjects` are read from the global sources in any case; a project's own never count.

**A key the project writes** follows this table, with one warning at startup that names the key and the way to change it. A key your entry does not set stays the project's to choose, under the rules above, with one exception: when your entry sets a `decision`, a threshold or `maxStateChars` it leaves out counts as its default, the value your model is judged by. Without a `decision` in your entry, the project decides them.

| Key | What a project's value does |
|---|---|
| `decision` | Ignored when it differs from yours in address, model, protocol, timeout, key or headers: your model stays. A project does not choose its judge. Written the same way, nothing changes. |
| `askAs` | `"deny"` is kept. `"ask"` over your `"deny"` is ignored. |
| `thresholds` | Each threshold on its own: a stricter one is kept, a less strict one is ignored, an empty or invalid one is ignored, and the others stay yours. Raising `denyNoul`, `askNoul`, `askExfiltration`, `denyRisk` or `askRisk`, or lowering `minConfidence`, is less strict. |
| `maxStateChars` | Ignored when it differs from yours: shorter, the model no longer reads the end of a long input; longer, it is less accurate. |
| `rules` | Added to yours. A rule with the identifier of one of yours, or of a built-in rule you set in `ruleOverrides` or `exceptions` (in your entry or a global `guard.json`, at the top or in a section), is ignored: yours stays. |
| `secretPatterns` | Added to yours. One of yours set aside with `enabled: false` stays active. |
| `ruleOverrides` | Rule by rule: what is at least as strict as your setting is kept; what is less strict, invalid or without effect on that rule is ignored, and your setting stays. |
| `rememberConfirmations` | A delay shorter than the one in force is kept. A longer one is ignored, and yours stays, with one exception: in a project's `opencode.json`, a delay shorter than the one of your global `opencode.json` counts even over a shorter one or `0` in your global `guard.json` or a `projects` section, without a warning (`3` over `5` there and `0` in `guard.json`); the same delay as your global `opencode.json` changes nothing. A project's `guard.json` has no such exception. |
| `unprotectedAgent` | Another name is ignored: yours stays. A value that is not a name is reported and leaves no such agent, which only hardens. |
| `allowlist`, `redactionOff`, `exceptions` | An entry you list too counts, and one you do not is ignored. |
| `profile`, `localAsks`, `selfProtectionByModel`, the switches | As in [the rules above](#relaxations-come-from-the-global-configuration). A switch you set to `true` stays on over a project's `false` or invalid value, also with the `credentials-only` profile. |
| `outputCheck`, `promptCheck` (settings) | Settings that differ from yours are ignored: yours stay. `true` or `{ "enabled": true }` keeps yours. See [the checks](decision-model.md#output-check-outputcheck). |
| `logFile`, `debug`, `cacheTtlMs`, `cacheMax` | The project decides: they change no verdict. `logFile` moves the log away from what `guard last` reads. |

**Values read back.** `{env:…}` and `{file:…}` references in a value kept this way are replaced as OpenCode replaces them, and the key and headers of a kept decision model are masked like those of the options. A `{file:…}` reference written outside a string makes the file unreadable for the plugin: nothing is kept, with the warning above. A kept value with a `{file:…}` reference stays what it is without a project: it certifies nothing, so such a decision model does not allow a confirmation, and such check settings are not kept.

**A project that needs something else.** `guard set` and the `projects` sections take the switches, the policy settings, `exceptions` and `rememberConfirmations`; a warning gives the command when one applies. They do not accept `decision`, `askAs`, `thresholds` or `maxStateChars`: a project that wants another model, or another value of these, goes through `trustedProjects`, where its own values count. In a trusted project, `rules`, `secretPatterns`, an invalid value and what it leaves out behave as above, and `unprotectedAgent` and `redactionOff` still count only from the global sources. Trust is read at startup: a project untrusted while OpenCode runs keeps these values until the next start.

## Settings by agent and by project (`guard.json`)

The **policy settings** (`profile`, `ruleOverrides`, `localAsks`, `selfProtectionByModel`, `dangerousCommands`, `sensitiveFiles`, `scripts`, `decisionModel`) can also be set for one agent, for one project, and in dedicated files; `exceptions` and `rememberConfirmations` too, except in an `agents` section. The other options (decision model, `askAs`, log, `rules`, redaction switches, `outputCheck`, `promptCheck`…) stay in the plugin options only, except `rules`, also read at the top level of the global `guard.json` (below), and the redaction switches, `outputCheck` and `promptCheck`, also read in a `projects` section of a global source (below); anywhere else they are ignored with a warning.

**Files.** `guard.json` in OpenCode's global configuration directory (the same one as above), and `guard.json` in a project's `.opencode` directory. Project files are looked up like OpenCode's own `.opencode` directories: in the session directory and every parent directory up to `/`, the closest one winning (so a `~/.opencode/guard.json` applies to every project under your home directory). OpenCode itself neither loads nor reports these files. A file is plain JSON, an object with the policy settings, `agents`, and in the global file only `projects`, `trustedProjects`, `redactionOff` and `rules`. It is read at startup and read again when it changes: the files are checked at most every 2 seconds, on the next tool call (and, for `redactionOff`, on the next redaction: a format turned back on is redacted again within 2 seconds), never read on every call. A file that is not valid JSON, is not an object, is larger than 64 KiB, is a symbolic link or cannot be read is ignored as a whole, with a warning that never quotes its content; an unknown key is ignored with a warning. Writing into OpenCode's configuration directories, `.opencode` included, already asks for your confirmation (self-protection).

**Your rules in the global guard.json.** `"rules": [ … ]` at the top level of the global `guard.json` takes the format of the `rules` option and is read with the same checks; its rules add up with the option's (an identifier used by both is reported with a warning, and both rules apply), and one without an `id` gets `guard-json-<index>` and the reason `custom rule <index> of the global guard.json`. Anywhere else (a project's `guard.json`, even a trusted one, an `agents` or a `projects` section) `rules` is ignored with a warning: a costly pattern in a repository would slow down every check. They follow each re-read of the file in every check (tool calls of every kind, CodeMode code, shell sub-commands, scripts run, `guard test`); a `ruleOverrides` or `exceptions` entry naming one of them is ignored, as for the option's rules. If the global `guard.json` becomes invalid while OpenCode runs (not valid JSON, larger than 64 KiB…), the rules read from it last stay in force, with an error in the log, until it is valid again; its other settings are dropped. Likewise while the file stays valid but its `rules` is no longer a list (the rules read from it last stay), and for an entry that becomes invalid (pattern, verdict): the rule read last under that identifier stays, with an error in the log. `guard test` and `guard rules`, which do not see what a running plugin read before, say so: they name each such identifier (never its pattern), and say when `rules` is not a list, as rules a running plugin may keep. Removing the file removes its rules; an invalid file at startup is ignored with a warning (no rule to keep). `guard rules add` and `guard rules remove` write them.

**Two layers.** The **global layer** is, from lowest to highest: the plugin options of your global configuration file, the global `guard.json`, then the `projects` sections that match the session directory. The **project layer** is what the effective plugin options change from your global file (a project's `opencode.json` can replace them), then the project `guard.json` files. The project layer is laid over the global one setting by setting: what makes the plugin stricter always applies; what makes it less strict applies only in a **trusted project**, and is otherwise ignored with a warning. For the effective plugin options, the rule of [Relaxations come from the global configuration](#relaxations-come-from-the-global-configuration) still holds (a value the global or system configuration also sets is kept).

**What relaxes.** A setting relaxes when it makes some finding less severe than the value it replaces: refusal, then confirmation, then a confirmation left to the decision model, then nothing (`"off"`). The plugin checks this on every built-in rule with the same functions it uses on each call, as if each rule could both refuse and ask: `"ask"` therefore counts as a relaxation for any rule (it would lower a refusal), even for a rule that only asks, where it in fact only hardens (and is set aside, with a warning, outside the global sources and trusted projects); likewise `"model"` for any rule while the decision model is on. `"localAsks": "model"`, `"selfProtectionByModel": true`, the `credentials-only` profile and a switch set to `false` relax; so does `"decisionModel": true` when confirmations are left to the model.

**Trusted projects.** `"trustedProjects": ["/home/me/work", "/home/me/src/app"]`, or `"*"` for every project, in the global configuration file, the system configuration or the global `guard.json` (anywhere else it is ignored with a warning: a project cannot trust itself). A project is trusted when its real directory is a listed one (real path) or below it: trusting a parent directory trusts every repository cloned under it later, including one you have not read. Each project `guard.json` file is judged by its own directory (the one holding its `.opencode`): a file above the trusted directory (in a parent directory, the home directory, `/tmp`…) only hardens. A listed directory that does not exist is ignored with a warning. A change of the global `guard.json` counts at the next check, without a restart.

**Projects.** `"projects": { "/home/me/work": { <policy settings>, "agents": { … } } }` in the same global sources: the section applies to that directory and below, in the global layer (it may relax), after the global `guard.json`; when several match, the closest directory comes last. A section also accepts `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck` and `promptCheck`, on or off (the settings of a check count only in the plugin options). These five are read when the plugin starts: a change in `guard.json` is reported in the log and counts from the next start, as `guard set`, `guard unset` and `guard show` say. A `true` in a project's options takes over a section's `false`, unless the global file sets the same `true`: nothing then tells the project's value from your own options, and the section's value stays. When the system configuration sets the key, its value keeps the last word, whatever the global file repeats.

**Relaxing one agent.** Besides the policy settings, a section of a global source accepts `"guard": "off"`, the switches `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck` and `promptCheck` set to `false`, and `models`, a list of `provider/model`. These are read from the global file, the system configuration, the global `guard.json` and its `projects` sections; never from a project, even a trusted one (a project `guard.json` may only take a relaxation back, with `"guard": "on"` or a switch at `true`; such a key in a project's plugin options is ignored with a warning). A built-in agent (`build`, `plan`…) cannot be relaxed.

```jsonc
"agents": {
  // The local rules stay; the model sees secrets in clear, on this model only.
  "n3": { "redactOutputs": false, "redactPrompt": false, "redactWire": false, "outputCheck": false, "promptCheck": false, "models": ["linagora/qwen3.8"] },
  // Nothing checked and nothing redacted, like `unprotectedAgent`, for as many agents as listed.
  "sandbox": { "guard": "off", "models": ["linagora/qwen3.8"] }
}
```

- **The keys work together.** For the model to see secrets in tool outputs, `redactOutputs`, `redactWire` and `outputCheck` must all be off; for what you type, `redactPrompt`, `redactWire` and `promptCheck`. The wire safety net alone (`redactWire` still on) masks known formats again.
- **Each request is decided on its own.** A relaxation applies only to the main agent you selected at your last prompt, in `primary` mode, in a root session, for the agent's own requests (`kind` `primary`): a title, a compaction or a generation stays redacted even under that agent's name. A subagent inherits nothing, unlike the policy settings. Unknown session or main agent, unattended mode (`askAs: "deny"`), or an invalid `models` (which then matches no model): nothing is relaxed.
- **`models`.** On the wire, the model of the request decides; for the prompt and tool outputs, whose hooks are not told the model, the session's model at your last prompt, or else its agent's. Without `models`, a change of model is not protected, and the log says so.
- **What always stays redacted:** the guard's log and everything sent to the decision model. With `redactPrompt` off and `promptCheck` on, the model checks a redacted copy and only decides whether the prompt leaves; nothing you typed is masked. The placeholder rule stays with `"guard": "off"`; with the switches alone, every rule stays.
- **Project.** A project cannot relax an agent, but it can still select or redefine one your global sources relax (`default_agent`, an agent file in `.opencode/agents/`), and a relaxed agent then runs from your first message: check the agent shown in the prompt bar when you open an unknown repository, the more so with several agents relaxed. The same gap as [`unprotectedAgent`](rules.md#unprotected-agent-unprotectedagent).
- **Stored history.** With `redactOutputs` or `redactPrompt` off, secrets are stored in clear in OpenCode's history. If the session later continues under another agent or model, the wire safety net masks known formats only, not a password written in plain words.

`guard agent off <agent> [--model <provider/model>]…`, `guard agent on <agent>`, `guard agent set <agent> <key> true|false`, `guard agent unset <agent> <key>` and `guard agent models <agent> <provider/model>…` write these keys in the global `guard.json`; `guard show` lists them with the `relaxes` mark. `guard agent off` keeps a `models` already in the section, unless `--model` replaces it. `guard agent models` refuses a value starting with `-`. `guard agent on` removes `guard`, the switches and `models` from the section and leaves its policy settings. Each of these commands ends with the agent's state: `fully protected` only when nothing in the global and system sources, or in a `projects` section of the global `guard.json` that has a section for this agent, relaxes it any more; otherwise what is left, by name, after `still relaxed:` (policy settings of its section or of the level above, exceptions, redaction turned off globally, `unprotectedAgent`). A trusted project's own `guard.json` is not read here: `guard show --agent <agent>` from that directory shows it.

**Agents.** `"agents": { "<agent>": { <policy settings> } }` in any source, also inside a `projects` section. For a call, the resolved layers come first, then the section of the **main agent** of the session, then the section of the **subagent** making the call, if it has one: `ruleOverrides` merge rule by rule, the other settings key by key. A subagent without a section uses the main agent's settings; a subagent's section may harden or relax them. A section from a project source follows the project layer: it relaxes only in a trusted project.

- The main agent is the session's agent when you sent your last prompt, provided its mode is `primary`; for a subagent's session, it is the main agent of the root session. It is recorded by the plugin at each prompt, while the settings in force have an agent section (otherwise no session is read): a section added while OpenCode runs counts from your next prompt. An agent switch made by the model during a turn does not count until your next prompt: only what the new agent's section makes stricter applies.
- When the main agent is unknown (plugin reloaded since your last prompt, no prompt since the first agent section was added, session that cannot be read, agent whose mode is not `primary`), only what makes the calling agent's section stricter applies: never less strict than the layers.
- **Risk.** The model chooses which subagent it launches. A subagent whose section relaxes a rule lets the model obtain that relaxation by launching it; keep relaxing sections for subagents whose purpose needs them.

```jsonc
// ~/.config/opencode/guard.json
{
  "ruleOverrides": { "git-reset-hard": "ask" },
  "agents": { "reviewer": { "dangerousCommands": false } },
  "projects": { "/home/me/sandbox": { "ruleOverrides": { "rm": "off" } } },
  "trustedProjects": ["/home/me/work/app"]
}
```

**Log.** The start line `settings by agent and by project (guard.json: …; agent sections: …; project sections: …; this project: trusted|not trusted)` lists the files read, the agents with a section, the matching project sections and the trust of the session directory; `guard.json re-read (…)` is logged at the info level each time the files change, followed by their warnings. Without any `guard.json` file and without `agents`, `projects` or `trustedProjects`, nothing changes and nothing is logged.

## The `guard` command

`bin/guard`, in the plugin directory, lists the rules and reads or writes these settings from a terminal. It runs with the Node.js found on the `PATH`, which reads the plugin's TypeScript files directly (no build step, no dependency): that Node.js must run TypeScript files without any option (a version that strips types by default; an older one refuses the launcher). A link makes it available everywhere, for example `~/.local/bin/guard` pointing to it.

A plugin that OpenCode installed from a Git specifier ([README](../README.md#from-git)) needs a launcher instead, since Node refuses TypeScript under `node_modules`. `tools/install-cli.sh` writes one to `~/.local/bin/guard`, or to the directory given by `GUARD_BIN_DIR`, which it creates if needed. It replaces an existing link without writing through it, stops with exit code `1` and installs nothing when the target is a directory or a link to one, and warns, without changing anything, when that directory is not on your `PATH`. The launcher reads the specifier from the global `opencode.json`, then runs the generation OpenCode loads with the Bun inside OpenCode: it needs no change when you change version, and stops with a message when no Git specifier is configured or the plugin is not installed yet. It reads that file as text, so a `"package"` line commented out in an `opencode.jsonc` above the real entry takes its place: delete such a line.

**The terminal's environment.** Every command reads the terminal's environment, not the OpenCode server's: the global configuration directory (`OPENCODE_CONFIG_DIR`, `XDG_CONFIG_HOME`, `HOME`), the `{env:…}` references of the configuration files, and for `last` the log file (`XDG_DATA_HOME`, `HOME`, `logFile`). When the server runs with another environment (a background service), the command may read other files than the plugin does.

**What it prints.** Every line goes through the plugin's redaction: its built-in formats, the `secretPatterns` and the decision model's key and headers of the global and system configurations, and the terminal's secret environment variables. It also replaces control characters (C0, line breaks included, C1 and bidirectional controls) with a space, as the plugin's log does: a repository's `guard.json` quoted in a line cannot change the display. In a terminal, `guard rules`, `guard redaction`, `guard show` and `guard last` print blocks, each under a banner of its own color and a separator line: the built-in rules grouped by the option that turns them off (or one rule's explanation, with its own headings, for `rules --explain`), your rules each with its pattern on the next line, the sources read, the project's trust, the settings in force (one color per value, `true` green, `false` red, a rule's setting in the colors of `guard rules`, and a `relaxes` mark for a setting that relaxes a protection), the exceptions in force (each marked `relaxes`, its origin under its path) and those set aside, the latest asks and denials by day with their reason below them. Columns are aligned and texts wrapped to the terminal's width (at least 60 columns), a confirmation's model opinion on a dimmed line of its own; headings, verdicts and states are colored unless `NO_COLOR` is set or `TERM` is `dumb`. Redirected to a file or another program, they print one line per item, as before. Each field is redacted before it is wrapped, and colors are added only to a line that the redaction leaves unchanged.

| Command | What it does |
|---|---|
| `guard rules [--builtins\|--custom]` | lists the built-in rules in the plugin's order (identifier, group, own verdict, what they check), then your own `rules` as the plugin reads them (identifier, verdict, tools, reason, pattern) from the system configuration when it declares the plugin, otherwise from the global one, then those of the global `guard.json` under their own heading, each list with the rules it sets aside and why; a project's `opencode.json` can replace the option's list, which the command does not see. `--builtins` or `--custom` keeps one of the two |
| `guard rules --explain <rule>` | explains one built-in rule in words: its group, own verdict, what it checks, how it decides, the reason a finding usually carries, and the settings that apply to it (the group switch and `ruleOverrides` values, and for `secret-file-read` its `exceptions` and `rememberConfirmations`); never its pattern. It cannot be combined with `--builtins` or `--custom` |
| `guard redaction [--builtins\|--custom]` | lists the redaction formats: the built-in ones with their state (`on`, or `off` when the global or system configuration turns them off) and what they catch, OpenCode's own (always active), then your `secretPatterns` with their regular expression, read like `guard rules`, and the entries set aside and why. `--builtins` or `--custom` keeps one of the two |
| `guard redaction --explain <format>` | one format: its state, what it catches, how it is replaced, every regular expression of its type, and how to turn it off. It cannot be combined with `--builtins` or `--custom` |
| `guard rules off <rule>`, `guard rules ask <rule>`, `guard rules deny <rule>`, `guard rules model <rule>` | sets the rule in `ruleOverrides` of the global `guard.json`; `--agent` and `--project` write it in that section. `guard rules off secret-file-read` turns the whole rule off, for every file, and says so |
| `guard rules off secret-file-read --path <file>` | adds the file's real path (relative to the current directory, symbolic links resolved) to `exceptions.secret-file-read` of the global `guard.json`, at the top level or with `--project` in that project's section, and says so when it differs from the path given; the rest of the rule is unchanged. Refused, nothing written: a missing file, a path that is not a regular file, a path with a `..` component, and a path the plugin would not retain there (its warning is the reason). `--path` with another rule, another setting or `--agent` is a usage error |
| `guard rules reset secret-file-read --path <file>` | removes that file from `exceptions.secret-file-read` (compared by real path, or by absolute path once the file no longer exists; a list or an object left empty is removed; a path with a `..` component is refused), and says if another source or section still excepts it for the project given, otherwise for the current directory |
| `guard rules add <id> --pattern <regex> --verdict ask\|deny [--reason <text>] [--tools <tool>[,…]\|*] [--flags <flags>]` | adds one of your rules to `rules` of the global `guard.json`, at the top level only (`--agent` and `--project` are usage errors; default tool: `shell`); a pattern or a reason starting with `-` is taken as is. Refused, nothing written: a verdict other than `ask` or `deny`, a pattern that is not a valid regular expression (compiled with the plugin's checks, by Node, while the plugin compiles it under Bun: a pattern one accepts and the other refuses would be written, then set aside with a warning), the identifier of a built-in rule, `internal-error`, `__proto__`, `constructor`, `prototype`, and an identifier already used by the `rules` option or the file. Its messages name the rule and its source, never its pattern |
| `guard rules remove <id>` | removes that rule from `rules` of the global `guard.json` (a list left empty is removed); a rule of the `rules` option is never removed (refused), and when both sources define it, the command says the option's stays; a rule written by hand under a built-in rule's identifier set aside the `ruleOverrides` of that rule, and the command says when one applies again |
| `guard rules reset <rule>` | removes that setting (an object left empty is removed), and says if the rule still does not apply there: another source still sets it, or its group (`dangerousCommands`, `sensitiveFiles`) is off, with the source that turns it off |
| `guard set <setting> <value> [--agent <name>] [--project [<dir>]]` | writes a policy setting in the global `guard.json`, at the top level or in that agent's or project's section: `profile` (`standard`, `credentials-only`), `localAsks` (`ask`, `model`), the switches `selfProtectionByModel`, `dangerousCommands`, `sensitiveFiles`, `scripts`, `decisionModel` (`true` or `false`, also `on` or `off`), with `--project` only and without `--agent` the switches `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck`, `promptCheck`, and `rememberConfirmations` (whole minutes, 1 to 60; `guard unset` turns it off; never set with `--agent`, a usage error). Refused, nothing written, when the plugin would not apply it there (its warning is the reason); when another source keeps the last word there (the system configuration), the command says so. For the switches read at start, it says they count from the next start. A rule's setting is changed with `guard rules` |
| `guard unset <setting> [--agent <name>] [--project [<dir>]]` | removes that setting there (an object left empty is removed), and says what is then in force there and where it comes from; with `--agent`, `rememberConfirmations` too (a value written by hand in an `agents` section, which the plugin ignores) |
| `guard redaction off <format>`, `guard redaction on <format>` | turns a built-in redaction format off, or back on, in `redactionOff` of the global `guard.json` (a list of format names, top level only: in a project's `guard.json`, an `agents` or `projects` section or `opencode.json` it is ignored, with a warning). Back on, a format that `redactionOff` of the global or system configuration also turns off stays off, and the command says so. An unknown name and OpenCode's own formats are refused |
| `guard trust [<dir>\|--all]`, `guard untrust [<dir>\|--all]` | adds or removes the directory's real path in `trustedProjects` of the global `guard.json` (`--all`: `"*"`) |
| `guard settings [--agent <name>]` | every setting of the plugin: its type, the value in force, its default (computed by the plugin's own reading) and where it comes from; a secret shows only `set`, a list only its size |
| `guard settings --explain <setting>` | one setting, or `all`: what it does, its accepted values and bounds, where it can be set, when a relaxation counts, and its state here, with an `{env:…}` reference resolved in the terminal (the server's environment may differ) |
| `guard show [--agent <name>]` | the plugin's commit and whether it is the HEAD or a tag (installed from Git: the commit OpenCode installed, compared with the repository by `git ls-remote`, at most 3 seconds, unless `--offline`; run from a repository: that repository), the policy settings in force for the current directory (and that main agent), each with the file and section it comes from, the delay of `rememberConfirmations` (`off` when not set), the exceptions in force (rule, real path, source and section; `none` when there is none), the project's trust, and the settings set aside with the reason; `redactOutputs`, `redactPrompt`, `redactWire`, `outputCheck` and `promptCheck` are marked as read when the plugin starts, and a check that is on but has no model it may use shows `inactive` with the reason (the running plugin's state is not read); also the number of your `secretPatterns`, each built-in redaction format turned off (marked `relaxes`) and the `secretPatterns` entries set aside |
| `guard last [<count>]` | the latest confirmations and refusals of the plugin's log (same file, `logFile` included), with their time in the terminal's time zone and its offset (the log itself stays in UTC), rule and reason as logged; 20 by default, at most 200. The previous copy (`guard.log.1`), read when the current file holds fewer, passes the same checks as the log: a link, or anything but a regular file, is left out without failing the command |
| `guard completion bash\|zsh` | prints a completion script for the shell: commands, options, rule identifiers, redaction formats, settings and their values. Load it from the shell's startup file, `eval "$(guard completion zsh)"` in `~/.zshrc` (or `bash` in `~/.bashrc`): generated at each shell start, its lists follow the plugin's version. zsh uses it through `bashcompinit` |
| `guard status [--offline]` | from the plugin's log: its latest starts (time and start line, an unavailable part shown), the settings the latest start refused, with the reason, the errors and warnings written after the latest one (a start's own warnings left out; several OpenCode instances may write the same log, so they may come from any of them), whether the plugin's files changed after it (not loaded yet); then one decision request on a harmless call, with its duration or the class of its failure (`--offline`: nothing sent). A log that cannot be found or read is reported as `state unknown`, with the reason. Exit code 0 whatever the state |
| `guard test [--agent <name>] [--model] [--] <command>` | the verdict the plugin would give to this shell command in the current directory (allow, ask, deny), with the rule and the reason, without running it: same rules and settings as the plugin (configuration, guard.json files, the agent's section, default agent `build`, exceptions included, each one that lifts the call noted), with the server's environment (`service.json` of the global directory completes the terminal's). Without `--model`, a call that no local rule decides is said to be the decision model's; with it, the model is asked (the call is sent to it). The memory of confirmations does not apply (it holds within a session): the command notes it for an ask it could lift. Options come first; the words after them (or after `--`) are the command. Not replayed: OpenCode's own permission rules, its second check of the shell sub-commands, scripts written earlier in a session, and options merged from a project's `opencode.json` |
| `guard test --tool <name> '<json input>'` | the same for another tool call, its input as OpenCode passes it (`--tool read '{"path":"~/.ssh/id_rsa"}'`) |
| `guard agent off\|on\|set\|unset\|models <agent> …` | what the section of an agent relaxes: see [Relaxing one agent](#settings-by-agent-and-by-project-guardjson) |
| `guard update` | a plugin installed from a Git specifier: runs `opencode plugin update <specifier>`, relays its output and exit code, and says whether the installed commit changed: see [Updating the plugin](operations.md#updating-the-plugin) |
| `guard update --check` | only runs `opencode plugin check <specifier>`, and relays its output and exit code |
| `guard help`, `guard -h` | the commands (`--help` too) |
| `guard <verb> -h`, `guard help <verb>` | the commands of this verb (`--help` too) |

**Exit codes.** `0`: done, or nothing to change (the value was already there, or already absent); `1`: refused or failed, nothing written (the reason is printed on stderr); `2`: usage error (unknown command, option or setting, a name that `rules --explain` or `redaction` does not know, an invalid count for `last`, missing or extra argument, an option that does not go with the command, such as `--path` with another rule or `--agent` with `set rememberConfirmations`), followed by the help on stderr; an unknown rule given to `rules off|ask|deny|model` is refused by the plugin's own warning (`1`). `guard` alone prints the help and exits with `2`, `guard help` with `0`; `guard test` exits with `0` whatever the verdict (allow, ask or deny) and with `1` for a `--tool` input that is not a JSON object; `guard status` exits with `0` whatever the state. `guard update` gives the exit code of `opencode` when it is not `0`.

**Scopes.** A setting goes to the top level of the global `guard.json`; `--agent <name>` writes it in `agents["<name>"]`, `--project [<dir>]` in `projects["<real path>"]` of the same global file, and both together in `projects[…].agents[…]`. Without a directory, the project is the first directory, going up from the current one, that holds a `.git` entry (directory or file), otherwise the current directory; no program is run to find it. `trust` and `untrust` without a directory take the same project. `--path` goes with `rules off` and `rules reset` of `secret-file-read` only, at the top level or with `--project`, never with `--agent` (an `agents` section accepts no exception); `set rememberConfirmations` never with `--agent` either (`unset` with `--agent` only removes a value written there by hand). A `projects` section lives in your global file: it takes effect without trusting the project and leaves the repository untouched.

**What it writes.** Only the global `guard.json`, in OpenCode's global configuration directory resolved from the terminal's environment as OpenCode does (`OPENCODE_CONFIG_DIR`, then `$XDG_CONFIG_HOME/opencode`, then `~/.config/opencode`); when the OpenCode server runs with another environment (a background service), check the path printed after each change. Never an `opencode.json`, never a project's `guard.json`. The file is replaced atomically (an exclusive temporary file in the same directory, then renamed), created with mode 600, its mode kept otherwise, and its unknown keys kept. If the file changed between the command's read and its write (another `guard` command, an editor), nothing is written: run the command again. Nothing is written, with the reason, for a file the plugin would ignore (symbolic link, not a regular file, unreadable, not valid JSON, not an object, larger than 64 KiB, or a result larger than that), a section that is not an object, a directory that does not exist (except for `reset` and `untrust`), and a value the plugin would not apply in that scope, with the plugin's own warning: unknown identifier, `internal-error`, one of your `rules`, `"off"` or `"ask"` on an always-active rule, `"model"` on one unless `selfProtectionByModel` is retained in the same scope (never for `guard-cli` or `placeholder`). `trust` warns for `/`, your home directory and `--all`: every project below becomes trusted, and its settings may relax yours. `guard update` writes nothing itself: it runs `opencode plugin update`.

**Without a restart.** The plugin checks its `guard.json` files at most every 2 seconds, on the next tool call: a setting applies from the following calls; an agent section counts from your next prompt, when the main agent is recorded.

**What `show` sees.** It computes the settings only from the files it reads itself: the global and system configuration, the global `guard.json` and the project ones. It does not see the plugin options OpenCode merges from a project's `opencode.json` (or `OPENCODE_CONFIG_CONTENT`), and says so: where they are set, the plugin may run with other settings, which its log shows at startup. A setting of the system configuration shows `system configuration` as its origin. It never prints another option of the configuration (decision model address, headers, keys…).

**No confirmation in the terminal.** The command asks nothing: what stops the agent is the plugin's own confirmation. Any shell command that runs it is a confirmation under the always-active rule `guard-cli`, whatever the subcommand (`rules`, `show` and `last` included): by its name `guard` as the program run (another program named `guard` asks too), or by the path of its launcher (a file `…/bin/guard` in any directory, so a link to it too) or of a module of the plugin's `src/cli/` directory, run directly or through an interpreter, or only named. Except in a command that only reads: plain words (no substitution, expansion, heredoc or group, no program that runs code named anywhere), each simple command one of `cat`, `head`, `tail`, `wc`, `ls`, `stat`, `nl`, `diff`, `grep`, `egrep`, `fgrep`, `rg` without `--pre`, `file` with options that only change its report, `git show`, `log`, `diff`, `blame` or `status` without an option that runs a program or a pager or writes a file, and `sed -n` printing line ranges; there the word `guard` in a quoted string or a path only named is not a launch, and `guard-cli` does not ask (that list is not the one that [exceptions](#exceptions-for-one-file-exceptions) lift, which leaves out `diff`). A reader made to run a program by configuration planted beforehand (a repository's git configuration, a startup file) does so whether or not the command names the command line. It is never left to the decision model, whatever `localAsks`, `"model"` or `selfProtectionByModel`; `"guard-cli": "deny"` refuses it outright. Another exception: the exact command `guard update --check`, alone, as written, which changes nothing; anything added to it asks, an assignment or a launcher before it included (a program named `guard` other than this one, run in this exact form, does not ask).

## Disabling

Remove the plugin entry from the `plugins` array in `opencode.json` (and from `/etc/opencode/opencode.json` or `OPENCODE_CONFIG_CONTENT` if you [use them](#protecting-the-plugin-from-project-configuration)), or restore the backup made before activation. To keep the local rules and redaction but disable the decision model, set `"decisionModel": false`, remove `decision.baseURL` or unset the key variable. To turn off only part of the plugin, see [Turning features off](#turning-features-off).
