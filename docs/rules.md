# Rules and redaction

## Local rules

Local rules are evaluated first and need no network access. Two options turn them off by group, `dangerousCommands` and `sensitiveFiles` (see [Turning features off](configuration.md#turning-features-off)); the placeholder rule, self-protection and your own `rules` always apply.

**Shell commands.** The full command is checked, then each segment (`;`, `&&`, `||`, `|`, `&`, new lines, `$(…)`, `<(…)`, `>(…)`, backticks). `rm`, `chmod`, `chown` and `chgrp` are also recognized right after a quote (`bash -c "rm -rf ~"`, `sh -c 'rm -rf /'`), and a device path may be quoted (`of="/dev/sda"`). Their targets are normalized before comparison (`//`, `/tmp/../*`, `/./` all mean `/`), for absolute paths and `~`/`$HOME` only: for these refusals, a relative path is never resolved against the working directory (protected writes are, see [Protected write locations](#local-rules)). zsh forms are recognized too, since the OpenCode service runs commands with your login shell: `{rm -rf /}` and `=rm` (zsh's path expansion) in command position, never after an identifier (`PAGER=less` runs nothing).

**Other tools.**

| Tool | Rule |
|---|---|

Before them, marked `hidden header`, it lists the headers found only in a piece of a line that does not itself start with a header: OpenCode reads such a line as content or refuses the patch because of it, and writes no file for it in either case, but the rule checks it, and it may be what a confirmation is about. When the list does not fit in its 200 characters, it starts with the number of hidden headers and of files |
| `webfetch`, `websearch` | secret anywhere in the input (URL, query, and any header or body field a future version may add) → `deny` |

Path arguments are the one-line strings under a key whose last word names a path (`filePath`, `filePaths`, `outputDirPath`, `directory`, `cwd`…) and, under any key, the strings shaped like a path (`/…`, `./…`, `../…`, `~/…`, `$HOME/…`) or `file:` URIs; free text and web addresses are not checked |

**Continued lines.** A command whose lines are continued (a backslash right before a line break, outside single quotes and heredoc bodies) is also judged with those lines joined, as the shell reads it; a finding of either reading counts. A command whose joined reading is not stable asks for confirmation.

**Code or data for another program.** A refusal pattern found only in code passed to a non-shell interpreter (`node -e "…"`, `python3 -c '…'`, `ruby -e`, `perl -e`, `php -r`, `deno eval`) or in the body of a heredoc becomes a confirmation, never less: for example test strings such as `node -e "…shellFinding('shred /dev/sda')…"`, or a heredoc that writes a file mentioning `curl … | sh`. Arguments in quotes (`rm -rf "/"`, `curl -d "@.env"`, `>> "$HOME/.bashrc"`) are still analysed as before. The refusal stands for the redaction placeholder, for your own rules, for a body expanded by the shell (`$(…)`, unquoted heredoc delimiter), and whenever the command also runs a shell outside that data (`bash -c`, `| sh`, `bash <<EOF`, `eval`, `ssh host "…"`, `watch`, a script run by its path or made executable). Accepted trade-off: `python3 -c "os.system('curl … | sh')"` asks instead of being refused. The same view applies to protected writes: `=>` in `node -e "x => …"` is not a redirection. Network access by the inline code itself is an exception: see “Network access by inline interpreter code” below.

**Confirmations caused only by heredoc data.** When a confirmation rule matches only inside heredoc bodies that are merely written or printed (`cat > test.ts <<'EOF' … EOF`, with `cat`, `tee`, `echo`, `printf`, `mkdir`, `touch`, `cd`, `ls`, `pwd`, `true` or `:` as the only commands), the decision model decides instead (allow, ask or deny), as for any command without a local rule; if it is unreachable, the confirmation stays. Typical case: a test script containing the string `sudo apt install x`. This never applies to your own rules, to refusals downgraded to confirmations, to code given to an interpreter (`python3 -c`, `node -e`, `python3 <<EOF`), to a body that another command receives (`docker exec -i c sh <<EOF`, `at now <<EOF`, a file written then run in the same command), to substitutions (`$(…)`, backticks, `<(…)`, `>(…)`), or to a `<<` inside quotes or a comment. OpenCode's own parsing of the sub-commands is still checked.

**Network access by inline interpreter code.** Code given inline to a non-shell interpreter, as recognized above (`node -e "…"`, `python3 -c '…'`, `deno eval "…"`…), is checked like a network tool run as a command when it makes network requests, as recognized by checks the plugin already has: a reference to `fetch` in code given to a JavaScript runtime (`node`, `nodejs`, `bun`, `deno`), Unicode escapes decoded as for CodeMode, or code that names `curl` or `wget` and calls a process or evaluation function (`system`, `subprocess`, `child_process`, `exec…`, `spawn…`, `popen`, a backtick…). A credential file or a detected secret in such a command is refused (an environment dump is not counted here); this refusal is not downgraded to a confirmation, since that code is run, not data. Otherwise the command asks for confirmation. Heredoc bodies are set aside, for the code as for the secret or the credential file, only when every command outside them is one of the data commands listed under “Confirmations caused only by heredoc data”, no substitution (`$(…)`, backticks, `<(…)`, `>(…)`) appears outside the bodies set aside (a body the shell expands, with `$(…)` or backticks, is never set aside), no `<<` stands inside quotes or a comment, and no shell is run outside them (as described under “Code or data for another program”); otherwise the whole command is examined, bodies included.

**Network tool run as a command.** A refusal requires the network tool to be the command actually run. Its name as a mere argument (`grep -i http .env`, `grep ssh ~/.ssh/config`) only leads to a confirmation. Environment dumps are `printenv`, `env` (with options only, e.g. `env -0`), `export`/`export -p`, a bare `set`, `declare -x`/`-p` and `/proc/<pid>/environ`; `set -e` or `env FOO=1 cmd` are not dumps. A key passed to `ssh`, `scp` or `sftp` with `-i` or `IdentityFile` authenticates and is not counted as sent (`ssh -i ~/.ssh/id_rsa host` asks), but `scp ~/.ssh/id_rsa host:` is still refused.

**Devices named indirectly.** The device refusals (`dd of=`, `shred`, a redirection, `tee`, the destination of `cp`/`mv`/`install`/`rsync`) also check their write target in canonical form, as protected writes do: surrounding blanks and quotes removed, a leading tilde or HOME variable expanded, repeated slashes, dot and dot-dot components merged, so `//dev/sda`, `/./dev/sda` or `/tmp/../dev/sda` is refused like `/dev/sda`. For a redirection, `tee` and the destination of `cp`/`mv`/`install`/`rsync`, the symbolic links of the target are also resolved, as for protected writes (see “Symbolic links” below): an absolute path that reaches a device through a link is refused, except in the case of the next sentence. A target that reaches a device only from one of the directories where the command may run gets a confirmation under the same rule instead of a refusal, since these refusals never resolve a path against the working directory: a relative target, directly or through a link, and a path through `/proc/self/cwd` or `/proc/thread-self/cwd`, which stand for these directories, written as such, with no quote or backslash inside its components, or reached through a link. Inside code or data for another program, these refusals become confirmations, as for a device written as is. A write target whose value is only known when the command runs (a variable, a command substitution, a wildcard) asks for confirmation, since it may be a device, when it is the `of=` operand of `dd`, a target of `tee` or the destination of `cp`/`mv`/`install`/`rsync`, run as the command of a segment: segments are cut even inside quotes, as for a device written as is, so a command given to `xargs`, `sh -c "…"` or `find -exec` counts only when it is itself the command of a segment. In code or data for another program, this confirmation is given only when the shell expands a command substitution in that code or body, or when the command also runs a shell outside that data.

**Credential files.** `.env` and `.env.*` (except `.example`, `.sample`, `.template`, `.dist`, `.defaults`), `id_rsa`/`id_dsa`/`id_ecdsa`/`id_ed25519` (not `.pub`), `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.p8` (PKCS#8 keys, also PICO-8 cartridges), `*.ppk` (PuTTY), `*.pk8`, `*.keytab` (Kerberos), `*.kdbx`/`*.kdb` (KeePass; sending one over the network is refused, like any credential file, so synchronize your KeePass database yourself), `*.heapsnapshot` (memory copies, such as the one the OpenCode server writes with `opencode debug heap-dump`), `.netrc`, `.npmrc`, `.pypirc`, `.pgpass`, `.git-credentials`, `~/.ssh/`, `~/.gnupg/`, `~/.aws/credentials`, `~/.aws/config`, `~/.kube/config`, `~/.docker/config.json`, `~/.config/gh/hosts.yml`, OpenCode's `service.json` (and `service-<channel>.json`) under `~/.config/opencode/` and `~/.local/state/opencode/`, or under the configuration and state directories that the server's environment gives (`OPENCODE_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`; absolute paths only) (server password, service environment); the output of the OpenCode subcommands that print these secrets or export the credentials counts as such a file when the same command runs a network tool (see “The server API”).

- **OpenCode's data directory** (`~/.local/share/opencode/`): `auth.json`, `mcp-auth.json`, `account.json` (API keys; no longer read by OpenCode 2.0.31, but it can remain on disk), and the database `opencode.db` (and `opencode-<channel>.db`, with its `-wal`, `-shm` and `-journal` files). In OpenCode 2.0.31, the database holds provider credentials (imported from `auth.json`), MCP OAuth tokens and account tokens, so reading it asks for confirmation (`sqlite3 ~/.local/share/opencode/opencode.db` included) and sending it over the network is refused.
- **Other coding agents' credential stores**, at their default locations: Claude Code (`~/.claude/.credentials.json`), Codex (`~/.codex/auth.json`, `.credentials.json`, `secrets/`, `.sandbox-secrets/`), Gemini CLI (`~/.gemini/oauth_creds.json`, `mcp-oauth-tokens.json`, `a2a-oauth-tokens.json`, `gemini-credentials.json`), GitHub Copilot CLI (`~/.copilot/config.json`, `mcp-oauth-config/`, `mcp-secrets/`), Kimi Code (`~/.kimi-code/server.token`, `~/.kimi-code/credentials/`, `~/.kimi/credentials/`, `~/.kimi/mcp-oauth/`), Pi (`~/.pi/agent/auth.json`), Amp (`~/.local/share/amp/secrets.json`, `~/.amp/oauth/`), Cursor (`~/.cursor/auth.json`, `~/.config/cursor/auth.json`, `~/.cursor/projects/<name>/mcp-auth.json`), Grok Build (`~/.grok/auth.json`, `mcp_credentials.json`), Factory Droid (`~/.factory/auth.encrypted`, `auth.v2.file`, `auth.v2.key`, `auth.v2.loginkeychain`) and Devin (`~/.local/share/devin/credentials.toml`, `~/.local/share/devin/mcp/oauth/`). The list is adapted from [cc-safety-net](https://github.com/kenryu42/cc-safety-net) 2.6.12 (MIT); their configuration files (`settings.json`, `config.toml`, `mcp.json`…) are not concerned.
- **Backup copies** of any of these files: a name ending with `.bak`, `.backup`, `.copy`, `.disabled`, `.old`, `.orig`, `.save` or `.tmp`, possibly numbered or dated (`.bak1`, `.bak.2`, `.bak-20261016`), or with `~` (editor backups): `.netrc.bak`, `server.key.orig`, `.env~`.
- **Private keys recognized by their content**, whatever their name: for a path named in a shell command (resolved from the directories where the command runs), given to `read`, `glob` or `grep`, or passed as a path argument of an MCP or plugin tool, the plugin reads the first 4 KiB of a regular file (never a named pipe or a device, nothing under `/dev`, `/proc` or `/sys`) and recognizes a file that opens with a PEM private key header (OpenSSH, RSA, EC, PKCS#8, PGP private key block), possibly after OpenSSL export attributes or a complete certificate, or a PuTTY key. A key quoted inside code or a document (test data) is not concerned. At most 2,048 paths are looked up and 128 files opened per check (the tool call, each script it runs, and again for the shell sub-commands checked at permission time); beyond that, and for a literal word longer than 1,024 characters, the check cannot finish and the command asks for confirmation (rule `secret-file-read`); what is read is never kept, logged or sent.

**Protected write locations.** Shell startup files (`.bashrc`, `.zshrc`, `.profile`…), `/etc/`, `~/.ssh/`, `.git/hooks/`, `~/.config/autostart/`, `~/.config/systemd/`, `~/.config/opencode/` (or the global configuration directory given by the server's environment), `.opencode/`, `opencode.json(c)` and the plugin directory. For shell commands, only real write targets count: file redirections (not `2>&1` or `/dev/null`), the arguments of `cp`, `mv`, `ln`, `install`, `rm`, `unlink`, `truncate`, `tee`, `touch` and `rsync`, and files edited in place (`sed -i`, `perl -i`). A relative target is resolved from the directory where the command runs, as OpenCode does: the shell's `workdir` (relative to the session directory) or the session directory, then the target of a leading `cd <path> &&` when the rest of the command is chained with `&&` and pipes only. When the command may change directory in any other way (another `cd`, `pushd`, `popd`, `env -C`, `sudo -D`, even the word `cd` in a quoted text), a relative target is protected if it is protected from any of the possible directories: the session directory, the `workdir` and each literal `cd`/`pushd` target. The shell sub-commands checked at permission time use the same directories. For a [script written then run](decision-model.md#decision-model), the session directory and the script's own literal `cd` targets are always added.

**Symbolic links.** Each write target is checked as written (surrounding blanks and quotes removed, a leading tilde or HOME variable expanded) and resolved lexically (repeated slashes, dot and dot-dot components merged) from the directory it is relative to: the session directory for OpenCode's `edit`, `write` and `patch` tools and for the path arguments of MCP and plugin tools, and each directory where a shell command may run (see above). For `edit`, `write` and `patch`, it is also checked exactly as these tools write it: from the session directory, with only a leading tilde (alone or followed by a slash) expanded and nothing trimmed (`patch` trims blanks around a file name, as its patch reader does, but keeps quotes). Each of these forms is also resolved on disk, link by link as the kernel does (a dot-dot component after a link goes up from the link's target); the strictest result counts. A write that reaches a protected location through a symbolic link is therefore recognized, and so is a write to the plugin's real directory when the plugin is loaded through a link. A missing part of the path (a file or directory to be created) is resolved lexically. `/proc/self/cwd` and `/proc/thread-self/cwd` stand for the directories where the command runs and for the OpenCode server's directory (its `edit`, `write` and `patch` tools write from the server process); the other entries of `/proc/self` (open file descriptors) and `/dev/fd` are not followed. At most 512 path components are looked up per check (the tool call, each script it runs, and the shell sub-commands checked at permission time) and 40 links followed per path; beyond that, for a loop of links, or for a path longer than 4,096 characters, the check cannot finish and the write asks for confirmation (rule `self-protection`).

## Secret redaction

Secrets are replaced with `[[GUARD_REDACTED:<type>]]`, for example `[[GUARD_REDACTED:openai_key]]`.

**Where redaction happens.**
- **At the source**, so the stored history and the UI stay clean: tool results (content, output, metadata), tool errors and their nested causes (message, stack, metadata and every other own field, such as `details` or the `reason` and `body` of a provider error — OpenCode shows the model the cause's message instead of the error's; `Map` and `Set` entries and regular expressions included), and the typed prompt (`redactPrompt`). Error copies keep their class, so OpenCode still recognizes a user's refusal. Cause chains are followed up to 32 levels; a deeper or cyclic cause is replaced by a placeholder rather than passed on unexamined.
- **A note for the model** is appended to the last text part of a tool result whose visible text was redacted: the placeholders mask secrets for display only, the file or data is unchanged, and the model must not try to rewrite or "fix" them (a model that sees its own value replaced may otherwise try to "repair" the file). The note is stored in the history, so you see it in the interface too. It is not added to valid JSON output (a CodeMode script may parse it), nor to tool errors. A CodeMode script receives the declared output of its inner tool calls, redacted but without the note (built-in and MCP tools all declare one; a plugin tool that declares none gives the script its text, note included); the note is appended instead to the script's result, which only the model reads, whenever one of its inner calls or the result itself was redacted, even if that result is valid JSON. It contains no `[[…]]` placeholder, so copying it never triggers the placeholder rule.
- **On the wire**, before anything reaches the provider: the JSON body of every model request over HTTP, including title and compaction requests, and WebSocket frames. This also covers attached files, `!` command output, background shell output and arguments generated by the model. Compressed bodies (`content-encoding: gzip` or `zstd`, which OpenCode uses when a provider sets `encoding`, and by default with a ChatGPT sign-in; `br` and `deflate` are handled too) are decompressed, redacted and recompressed with the same encoding. A body in another encoding, one that cannot be decoded, one whose type is not JSON or that is not valid JSON, and a WebSocket frame that is not JSON, are sent unchanged and reported once per cause in the log (`request body not inspected, secrets NOT redacted`, `frame not inspected`). If the redaction of a request fails (internal error), the request is not sent: the session stops with the plugin's message, and since the content that causes it stays in the history, every retry fails the same way; start a new session, or remove that content.

**What is detected.**
- **Known provider formats:** Anthropic, OpenAI, Google API keys, AWS access keys, GitHub tokens and fine-grained PATs, GitLab, Slack tokens and webhooks, Stripe, npm, Hugging Face, JWTs, PEM private keys and PGP private key blocks (`gpg --export-secret-keys --armor`; full or truncated blocks, up to 64 KiB after the header: in a larger block, such as a key exported with a photo ID, what follows the first 64 KiB, including any further private subkey, is not masked; a text that merely quotes the marker, public keys and signatures are left alone).
- **Credentials in context:** `Bearer` tokens (not a plain word: "Bearer internationalization" is left alone), `Basic` credentials in any case, only when they decode to `user:password` (an empty password included, as in `curl -u key:`; "Basic internationalization" is left alone), passwords in URLs (`scheme://user:password@`, up to the last `@` of the host part, so a password containing `@` is fully redacted; the user name may be empty, as in Redis URLs).
- **Next to a placeholder:** a value stuck to a placeholder (`PASSWORD=[[GUARD_REDACTED:…]]s3cret`) is still redacted; already redacted text stays unchanged.
- **Generic assignments** such as `API_KEY=…`, `"client_secret": "…"`, `password: …`, `GPG_PASSPHRASE=…`, `DB_PASS=…` (`pass` only as a whole name or last component, with `=` or `: `; not `bypass`, nor `pass:entry`, a reference to the `pass` password manager) and options followed by their value (`--password …`, `--token …`, `--api-key …`). Only the value is redacted, surrounding code punctuation is kept (`{password: …}`, `connect(token=…)`); an unquoted value continues after a comma (`DB_PASSWORD=abc,def`) except before a neighbouring named argument (`f(password=…,user=…)`), and stops at a literal escape (`\n` in JSON text); values may contain `$` (`$uper$ecret1`), but values that look like code (`process.env.X`, `config.apiKey`, `${…}`), a lone variable reference (`$DB_PASS`), a path after `pass`, or a placeholder (`changeme`, `<your-token>`) are left alone.
- **Quoted passphrases** after an environment-style name in capitals ending with PASSWORD, PASSWD, PASSPHRASE, SECRET or PASS (`DB_PASSWORD="velvet orbit …"`, `export GPG_PASSPHRASE='…'`): the whole quoted text is redacted (`[[GUARD_REDACTED:passphrase]]`). Templates (`%s`, `${…}`) and example phrases (`"your secret here"`, `"change me"`) are left alone, and so are lowercase keys (`password: "Mot de passe"` in a translation file), since a redacted line can no longer be edited (placeholder rule).
- **Configured secrets:** the decision model key (`decision.apiKey`, also when given under the former name `jev`) and header values, replaced verbatim (`[[GUARD_REDACTED:config:decision.apiKey]]`), wherever they come from.
- **Base64-encoded secrets:** a base64 block (24+ characters, including `base64` output wrapped at 76 and indented lines) is decoded; gzip content (`gzip -c f | base64`, `tar czf - … | base64`) is decompressed first (truncated streams included; of a content larger than 4 MB once decompressed, only its beginning, up to 4 MB, is examined). If the printable text (extracted like `strings`, so binary data around it or an archive does not hide it) contains any of the above, the **whole block** is replaced with `[[GUARD_REDACTED:base64]]`. Double encoding is covered.
- **Hex dumps:** two or more consecutive lines in the `xxd` format (all its variants: `-u`, `-g`, `-c`) or the `hexdump -C` format are decoded the same way (gzip included); a dump that contains a secret is replaced in full with `[[GUARD_REDACTED:hexdump]]`. The replacement stays visible (it is not re-encoded), so writing it back is still caught by the placeholder rule. Example: `base64 config.yml` on a file holding `DB_PASSWORD: …` does not give the model the password.
- **Secrets typed in the prompt in plain words** (prompt only): `mon mdp est …`, `mot de passe : …`, `my password is …`, `le token est …`, `clé API : …`, `api key -> …`. After `est`/`is`/`c'est`/`vaut`/`→`, or with no separator (password keywords only), the value must look strong (a symbol, or upper case, lower case and a digit), so `le token est base64url` is left alone; paths and URLs are never redacted. Whenever the prompt is redacted (by these words or by the other patterns), a note is appended to it so that the model asks you for the secret another way instead of guessing it. Not detected: a bare password without a keyword.
- **Your real secrets:** the values of the server's environment variables whose name contains API, AUTH, BEARER, CREDENTIAL, KEY, PASSWORD, PASSWD, PASSPHRASE, SECRET or TOKEN anywhere (in any case), or PASS as a whole component, and of the fixed-name passwords `MYSQL_PWD` (MySQL and MariaDB client) and `SSHPASS` (sshpass), are replaced verbatim (at least 12 characters, excluding paths and URLs without credentials; values with spaces only for PASSWORD, PASSWD, PASSPHRASE, SECRET and PASS names and the two fixed names).
- **OpenCode's own secrets:** the service password and the remote-access route are replaced verbatim (at least 8 characters). They are read from OpenCode's service files (`service.json` or `service-<channel>.json` in OpenCode's configuration and state directories: `~/.config/opencode/`, or the directory named by `OPENCODE_CONFIG_DIR`, and `~/.local/state/opencode/` by default) and read again when the files change; a password seen once stays masked after it changes, until OpenCode restarts or reloads the plugin (the last 1,000 values seen). Credential values in the format printed by `opencode auth export` and by the server API's credential list (the `key` of a key credential, the `refresh` and `access` tokens of an OAuth credential, when the value has the shape of a key or token: at least 20 characters among letters, digits and `._~+/=:-`, varied enough, written with the characters of a key format rather than those of a path, a host name, a setting name or words joined by dashes, and not a keyboard shortcut or an address) and the pairing code in pairing links (`…/auth/connect/<code>`) and in the server API's pairing answer are redacted, then masked wherever they appear again, even alone, until OpenCode restarts or reloads the plugin (up to 1,000 such values; beyond, a new value is redacted only in its format). The QR code printed by `opencode pair` (ten or more lines of block characters) is replaced in full (`[[GUARD_REDACTED:qr_code]]`).

**What is left untouched.**
- **Binary payloads.** A string that is **entirely** a well-formed binary `data:` URL (image, audio, video, font, PDF, archive) is skipped; a `data:image/…` prefix followed by anything else is analyzed. Strings of 10,000+ characters made entirely of base64 (images in a request) are decoded and their printable text checked, but the patterns are not run on the base64 text itself; your known secret values (environment, configuration, OpenCode's own) are still looked for in it and replaced alone. Text `data:` URLs and long texts are analyzed.
- **Signed blocks.** Provider-signed blocks are never modified on the wire: objects of type `thinking`, `redacted_thinking` or `reasoning`, or carrying a `signature`, `encrypted_content` or `thoughtSignature` key. Changing them would make the provider reject every retry. The predicate is deliberately broad: OpenCode's protocols use many signed shapes without a recognizable `type` (Bedrock `reasoningText`, Gemini parts, Venice, OpenAI chat `reasoning_details`…). The residual risk is low: tool outputs are already redacted at the source, without this exception, and signed blocks come from the provider itself. Two exceptions: the arguments of a tool call (Anthropic `tool_use.input`, Bedrock `toolUse.input`, Gemini `functionCall.args`), which OpenCode serializes verbatim, are redacted even if the model puts a `signature` key in them, except in a Gemini part that carries a real `thoughtSignature` next to its `functionCall`: that part is left whole, its arguments included; and a Gemini part carrying the sentinel `skip_thought_signature_validator` (added by OpenCode when replaying a call without a signature) is not treated as signed.

**Cost.** The built-in patterns are written to run in time proportional to the length of the text, including on inputs built to be unfavourable (long texts without spaces such as base64url, minified code or chained identifiers). This matters because the hooks are synchronous: OpenCode waits for the redaction. Patterns added with `secretPatterns` are your own regular expressions and carry no such guarantee: avoid nested repetitions such as `(a+)+`.

**Placeholder protection.** Any attempt to write the placeholder into a file (`edit`, `write`, `patch`, shell, CodeMode, MCP) is denied, because it would overwrite the real secret. The agent is asked to make a targeted edit that does not include the placeholder. This includes a placeholder encoded in base64 (up to two levels), such as the `data:` values of a Kubernetes Secret or a `.dockerconfigjson`, which would otherwise be written back over the real values.

## Confirmations and run modes

- **`--auto`** (and its hidden aliases `--yolo` and `--dangerously-skip-permissions`) is handled **by the client**: OpenCode's server still raises every confirmation request, and the CLI (or the TUI in "autoaccept" mode) answers "allow once" automatically. All of the plugin's confirmations are therefore approved; only `deny` verdicts still protect you. The plugin cannot detect this mode, hence the unattended mode below.
- **Non-interactive `opencode run`** (without `--auto`). Confirmations are auto-rejected and the model continues without the action.
- **"Always allow"** is not remembered for the plugin's confirmations: each action judged dangerous is asked again.
- **`.env` reads.** Reading a `.env` file triggers two prompts: the plugin's, then OpenCode's built-in `*.env` rule.
- **Your own `!` commands** are never blocked; only their output is redacted on the wire.

### Unattended mode (`askAs: "deny"`)

For autonomous runs, set `askAs` to `"deny"`, typically through `"askAs": "{env:GUARD_ASK_AS}"` in `opencode.json`: every confirmation request becomes a refusal, so nothing that would normally require your approval runs unattended. It covers:

- the plugin's own confirmations (local rules, decision model verdicts, decision model unavailable, internal errors);
- OpenCode's native confirmations seen by the plugin, including the built-in `read *.env` rule and your own `ask` permission rules.

Actions that the decision model allows are not confirmations and still run in this mode, including a CodeMode script that uses `fetch` without referring to `tools` or writing a local address (see [Local rules](#local-rules)).

The model receives an explicit reason, e.g. `[guard] Blocked (rule git-reset-hard): confirmation required, but unattended mode (askAs: deny) denies it: git reset --hard (uncommitted changes lost)`. The plugin log states the effective mode at every start (`INFO active (…; confirmations: denied (unattended mode))`), so a misspelled variable, which silently yields `"ask"`, is visible there.

With `"askAs": "{env:GUARD_ASK_AS}"`, the variable must reach the **server**, since the configuration is read there. Use `--standalone`, which starts a private server that inherits the CLI's environment:

```sh
GUARD_ASK_AS=deny opencode run --standalone --auto "…"
```

Setting it on the background service (`opencode service set env GUARD_ASK_AS deny`) would apply to **all** sessions, including interactive ones, which would lose every confirmation prompt.

### Unprotected agent (`unprotectedAgent`)

With `"unprotectedAgent": "build-unprotected"`, the plugin adds a primary agent of that name (same permissions as `build`, unless your configuration defines it) that you select with **Shift+Tab**. For that agent the plugin does nothing: no local rule, no decision model, no confirmation, and **no redaction** (tool outputs, prompt, requests sent to the provider). One exception: writing a redaction placeholder into a file is still refused, because a session started with another agent contains placeholders and writing one back would destroy the real secret. OpenCode's own permissions (such as `read *.env`) still apply.

**Only your choice counts.** The agent is unprotected only if it was the session's agent when **you** sent your last message (the TUI switches the agent just before sending). If the session is switched during a turn by anything else, for example through the server API, it stays protected until your next message. Sub-agents launched by the model (they run a sub-agent such as `general`), a session with no message from you since the plugin was (re)loaded, an unknown agent, and an agent redefined by a project as `all` or `subagent` (which a model could launch) are always protected. In unattended mode (`askAs: "deny"`) the agent is not created at all: `opencode run --agent build-unprotected` stops with `Agent not found`.

**What to know.**
- A sub-task started by a `/command` from this agent (a command run as a sub-agent without its own `agent:`) inherits it and is unprotected too, since you started it.
- Everything this agent sees reaches the provider unredacted, including the earlier history of the session, attached `@` files, skills and instructions; a compaction summary made with this agent is stored unredacted. Back on a protected agent, the wire safety net masks known formats again, but not passwords written in plain words.
- What you type with this agent can also reach **other providers** than the one of the current model: the session title is generated by the `title` agent, possibly with another model, from your first message, and may be generated again from it and the recent conversation (only known formats are masked there, not a password written in plain words), and if you later switch the session to a model from another provider, the whole history, unredacted parts included, is sent to it. Do not type a real secret with this agent unless you accept that.
- A project can still select or redefine this agent (`default_agent`, a project command with `agent:`), and since a project can replace the plugin's options, it could even turn `unprotectedAgent` on and make it the default agent, so that your first message runs unprotected: same family as the [project configuration](configuration.md#protecting-the-plugin-from-project-configuration) gap (a project can already remove the plugin). Check the agent shown in the prompt bar when you open an unknown repository.
- A client other than the TUI that sends a message without re-selecting the agent (web, ACP) records the agent the session currently has.
- Permissions that your configuration gives to `build` are not copied (the agent is created before the configuration is applied); declare them for this agent too if you need them.

**The server API.** Anyone holding the OpenCode server password (`~/.config/opencode/service.json`, `~/.local/state/opencode/service.json`, or the same files under the directories given by the server's environment) can bypass the guard with or without this agent: switch a session's agent, send a prompt or a command on your behalf, or answer a confirmation request. Both files are therefore credential files for the local rules (reading them asks, sending them over the network is refused), and a shell command that calls `/api/session/<id>/agent`, `/command`, `/prompt` or `/permission`, or OpenCode 2.1's route that replaces a voice call's instructions (`/api/experimental/voice/session/<id>/instructions`), asks for confirmation. A URL built piece by piece or a script file escapes that last rule; the decision model judges it. OpenCode's command line reads the password by itself, so its subcommands are checked as well; a call that contains a backquote, or that ends at one (also just after the closing quote of the shell text it is in), asks for confirmation, even when the backquote sits inside quoted text. Otherwise, `opencode api` gets no local finding for a read: one of the read operations of OpenCode v2.1.1's API named by its identifier, `GET` (in any case) on one of their paths written without `.`, `..` or `%` (a query string is allowed inside a quoted path), the API description `/openapi.json`, or no operation at all (the list of operations). Any other call asks for confirmation: a write, a read that hands out secrets or files (the credential list, the configuration documents, a file, a pairing connection), an operation, a path or an option the plugin does not know, a value known only when the command runs, or a word split in a doubtful way (a body with blanks, for example). `opencode service get` asks unless its key holds no secret (`disabled`, `remote`, `hostname`, `port`, `cors`), and `opencode pair`, `opencode auth export` and `opencode debug heap-dump` ask too. Printing the password, the environment or the settings of the service, exporting the credentials or calling the credential list, in a command that also runs a network tool, is refused like sending the files themselves.
