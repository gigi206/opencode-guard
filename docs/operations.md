# Operations

## Logs and verification

**Plugin log.** When OpenCode runs as a background service, the plugin's stderr goes nowhere useful. The plugin therefore writes to `~/.local/share/opencode/log/guard.log`:
- the start line (`INFO active (…)`, with the decision model, the effective confirmation mode, whether the [system configuration](configuration.md#protecting-the-plugin-from-project-configuration) declares the plugin, the [profile](configuration.md#profile-profile) and the [rule settings](configuration.md#setting-one-rule-ruleoverrides) retained, when set, `profile: …` and `rule overrides: …`, the [features turned off](configuration.md#turning-features-off), `disabled: …`, and, when it is requested, whether the [output check](decision-model.md#output-check-outputcheck) is active) and warnings are always written;
- confirmations and refusals of tool calls are always written (`INFO`), with the rule that gave them (`(local, rule git-reset-hard)`; a verdict of the decision model alone has none, its reason says why), including those added by the check of shell sub-commands (`shell sub-commands → …`) and the refusals of unattended mode, and so are the answers to confirmations (`confirmed by the user`, or `confirmation not granted` with the error class, never your feedback text);
- allowed actions and redaction counts are written only when `debug` is `true` (`DEBUG`);
- a decision line ends with the duration of the model calls (`[model 640 ms]`, and `, 2 attempts` after a timeout was retried) and gives the source of the verdict (`(local)` for a local rule, `(model)` for the decision model, `(model-error)` when it failed, `(default)` when no model gave the verdict (decision model turned off, or an internal error), `(read-only)` for a read not sent to the model, `(task-list)` for `todowrite`, `(cache)` for a verdict reused from the cache) and, for an allowed action, the highest probability (`highest: credential access 0.43`), useful to calibrate `askNoul`;
- it contains only the tool name, the verdict, the rule, the reason and counts, and every line also goes through the redaction (defense in depth: a server response or an internal error message); the decision model URL is shown without credentials, query string or fragment;
- if an optional part fails to start, the guard still loads and the start line says so: `unprotected agent: UNAVAILABLE` (every agent stays protected), `secret redaction: INCOMPLETE` (secrets may reach the provider) or `output check: UNAVAILABLE`;
- each entry is a single line: line breaks and control characters (from a path chosen by the model or a server response) are replaced by spaces, and an entry longer than 8,192 characters after redaction is shortened in the middle (`…[N characters omitted]…`), keeping its start and its end;
- above 5 MB the file is renamed to `guard.log.1` (one copy kept), at startup and while running (size checked every 100 entries).

```sh
tail -f ~/.local/share/opencode/log/guard.log
tail -f ~/.local/share/opencode/log/guard.log | grep ' INFO '   # confirmations and refusals only (and start lines)
```

Typical lines:

```
INFO active (decision model: nox-4b via https://ai-gateway.example.com/v1 (chat); confirmations: ask; system config: not enforced)   # every start
WARN decision.apiKey is empty (is the variable referenced with {env:…} set …): decision model disabled # key missing
WARN unattended mode (askAs: deny): every confirmation request is denied                              # unattended mode
WARN redaction of model requests disabled (redactWire: false): only what is redacted at the source …  # feature turned off
DEBUG shell → allow (model): nox-4b: risk 0.14/3, highest: data destruction 0.05 [model 640 ms]
DEBUG read → allow (read-only): read-only tool, no local rule matched
INFO shell → ask (local, rule git-reset-hard): git reset --hard (uncommitted changes lost)
INFO shell → confirmed by the user
INFO shell → deny (local, rule pipe-to-shell): running a downloaded script (download piped to a shell or an interpreter)
INFO shell sub-commands → ask (local, rule git-clean): git clean -f (untracked files deleted)
DEBUG execute.after read: 2 secret(s) redacted
```

**Why a call was asked or refused.** A confirmation shows the rule, the reason, the decision model's opinion and the tool call's summary in its action (`Call tool guard · <rule>: <reason> — <opinion> · <tool call>`; the interface repeats the action on its `Tool:` line), as much of them as fits in 120 characters; for a decision without a rule, `guard · <reason> · <tool call>`. The full reason is in the log. A refusal is the tool's error, which the agent receives: OpenCode shows it in red under a shell command, an edit or a patch; for a tool shown on one line (read, search, `webfetch`, a refused `write`), the line turns red and the message appears when you click it. In both cases the log has the full line, with the rule.

**Checking that the plugin is loaded.**
- `opencode plugin list`, run from a project directory, should show `guard  local  /path/to/plugin_opencode/index.ts`. The first call from a directory the service has not opened yet may answer "No plugins found"; run it again from the same directory.
- `~/.local/share/opencode/log/opencode.log` should contain `loading plugin`, and neither `failed to load plugin` nor `configured plugin path must be a directory`.

## Updating the plugin

For a plugin installed from a Git specifier that follows a branch or a tag ([README](../README.md#from-git)):

- `guard update --check` runs `opencode plugin check <specifier>` and nothing else;
- `guard update` runs `opencode plugin update <specifier>`, always with the specifier, so that no other plugin is updated, then compares the commit in the lock file of the generation OpenCode loads, before and after: it says the old and new commit, or that nothing changed.

Both relay OpenCode's output and its exit code, at most 60 seconds for the check and 5 minutes for the update. `opencode` is looked up in `PATH`, with the terminal's environment and current directory.

After a change of commit, the `files` line of `guard status` says whether the new files are loaded; if they are not, restart the server.

Nothing is run for a plugin loaded from a directory, which is updated with Git there. Nothing is run either for a specifier pinned to a full commit: `guard update` is refused, `guard update --check` says there is nothing to check (exit code `0`). To change that commit, edit it in the plugin entry of `opencode.json` and in its `plugin.use` policy, then restart the server.

An agent gets a confirmation for `guard update`, under the rule `guard-cli`, as for the other commands of `guard`, and for `opencode plugin update`, under `self-protection`. Neither is left to the decision model. `guard update --check`, exactly and alone, asks nothing.

## Known limitations

- **Not redacted:**
  - GitHub Copilot's internal "utility" title request, which bypasses the hooks;
  - OpenCode's direct generation (`Generate.text`, and in OpenCode 2.2 the text, image and decision generation of the server API and the `image_generate` tool, whose prompt the model writes), which has no hook and sends only what its caller provides (a secret in a tool's arguments is still refused before the call);
  - with OpenCode 2.2's "Claude Agent" provider, everything sent to it: it runs the local `claude` program instead of HTTP requests, so the wire safety net does not see its requests (what is redacted at the source, tool outputs and the prompt, stays redacted); Claude Code also keeps its own copy of the conversation; the plugin says in its log when this provider is connected;
  - images and most PDFs and Office documents (see “Files the plugin cannot read” below);
  - encrypted contents and signed reasoning blocks: a secret in a signed block leaves as it is, with a warning in the log (see “Signed blocks” in [the rules](rules.md));
  - voice calls: what a client sends to start a voice call or, in OpenCode 2.1, to change its instructions is relayed by the OpenCode server to the voice provider, outside the hooks;
  - raw files under OpenCode's `tool-output` data directory (full outputs of truncated tool results, shell command output files, binary contents returned by MCP tools), which are not sent unless read again;
  - in OpenCode 2.2, the raw output of a scheduled task's condition kept in its state, and the files of artifacts under OpenCode's data directory.
- **Model-generated tool arguments** are redacted on the wire but stored as-is in the local history; so is a secret the decision model finds in the output of one of your `!` commands.
- **False positives:**
  - a secret in MCP tool arguments or in CodeMode code is denied;
  - an MCP or plugin tool that only reads a protected location (`/etc`, `~/.ssh/`, OpenCode's configuration) asks for confirmation, since the plugin cannot tell whether the tool reads or writes;
  - an MCP tool whose path argument names a remote file (for example in a hosted repository) is checked as if the path were local, so a remote name that looks like a credential file or a protected location asks for confirmation;
  - running a file created by the agent that is larger than 64 KiB, or that is a credential file, asks for confirmation every time, since its content cannot be checked (until OpenCode restarts or reloads the plugin, see “Scripts written then run” below);
  - in a command that uses a network tool, a variable whose name contains a secret word without holding a secret (an authentication server's address, a sort key) asks for confirmation;
  - a server environment variable whose name contains one of the secret words inside a longer word (`AUTH` in `GIT_AUTHOR_EMAIL`, `KEY` in a sort-key setting) has its value redacted like a secret, and a file that contains that value can then no longer be rewritten (placeholder rule);
  - a password-like value in code may still be redacted;
  - your own fake secrets in test fixtures are redacted when read;
  - a value that is not a secret but has the shape of a key, printed in the format of an OpenCode credential, is learned and masked everywhere until OpenCode restarts or reloads the plugin, and a network command that names it is then refused;
  - code given inline to a JavaScript runtime that only mentions `fetch` (in a string, a comment or a `git fetch` it runs), or code that names `curl` or `wget` while calling a process function for something else, asks for confirmation, and is refused if the command also holds a secret or names a credential file;
  - inline interpreter code that is only text is checked for network access as if it were run, whether it is given as an argument of another command (`echo node -e "…"`) or written into a heredoc body that is not set aside (see “Network access by inline interpreter code”), for example when the same command also runs a command other than the data commands listed under “Confirmations caused only by heredoc data”;
  - the path of `mkfs`, `wipefs` or `dd` preceded in the same word by `=`, an opening quote or `${` (a variable assignment, an option value, quoted text, a parameter expansion), and these names written right after `${`, can be refused even where the tool would not run (for `dd`, only with a device output in the same call or among the words of a launcher before it);
  - an unquoted command substitution after `git checkout` counts as several arguments, since the shell may split it into several files: a commit computed this way (`git checkout $(git rev-parse HEAD~1)`) asks for confirmation.
- **Detection gaps:** the local rules are pattern-based, and the decision model misses some cases, such as a `webfetch` sending encoded data in its URL. The home-directory `mv` rule only sees `~`, `$HOME` and absolute paths: `mv Documents …` run from the home directory is judged by the model. Network access by inline interpreter code is recognized only by the checks described in [Local rules](rules.md#local-rules); any other way such code reaches the network is left to the decision model. So a credential file that such code reads and sends in another way (a library or module called under another name or kept in a variable, a URL kept in a variable for a function that also reads files, a file passed through a variable to a remote connection program) gets the confirmation of a credential file read, which the decision model may decide with `localAsks: "model"`, whereas the same file sent by a network tool that the shell runs is refused. A file that the code only prints, piped by the shell to a network tool, gets a confirmation the model does not decide. Code that the recognition of inline code does not cover, including code given in a file or on standard input, is not concerned (for a file written earlier in the session, see “Scripts written then run” under [Decision model](decision-model.md#decision-model)). Once confirmed, what the code sends is not checked again. An OpenCode subcommand that prints a secret counts as a credential file in inline interpreter code only when the code gives the subcommand directly to a process call that also runs a network program, or makes network requests (as recognized above) and gives the subcommand directly to a process call (a literal, or a list of literals, just after the opening of that call; a backtick literal outside JavaScript), outside a comment of the code (`//` and `/* */` in JavaScript, `#` in Python, Ruby and Perl, all three in PHP). When that code also names a network program after a pipe or another shell separator (the subcommand only printed, or launched by another call), a confirmation the command already gets, including one that the self-protection rules give for this code (such as `opencode-service`; see “What inline interpreter code launches or writes” in [Local rules](rules.md#local-rules)), becomes the one a credential path at the same place gets: never left to the decision model, and a refusal only when your settings refuse that path (`secret-file-network` set to `deny`, or one of your own rules with that identifier), not where the path is refused because the shell expands the code; without a confirmation, nothing is added, unless only your settings turned off the rules that give one (`dangerousCommands` off, or a rule such as `upload` set to `off`). Printed, captured or kept in a variable, then sent by another process call or by the code's own requests, it gets the confirmation of the network program, of the code or of `opencode-service` instead, which the decision model may decide with `localAsks: "model"` (when the code also launches a process, only with `selfProtectionByModel` too), whereas a credential path written at the same place is refused or asks.
- **Command names:** the rules do not all recognize the launched program the same way. Several recognize a command only by its bare name or by some of its spellings; written otherwise, the command is left to the decision model for those rules, so the same command can be refused or confirmed under one spelling and not under another. Conversely, a few rules look for a program name without checking that it is the program the command launches, and can refuse or ask for a command that only mentions it. The command word is read as the shell reads it (quotes, escapes, bash's `$'…'` quoting) for each command of the command line (not after a reserved word of the shell such as `then` or `do`), of a subshell or group and of a heredoc read by a shell, and within the first nine words behind a program that runs its other arguments as a command (`env`, `nohup`, `exec`, `xargs`, privilege or time-limit wrappers…) or `find -exec`, command substitutions included down to two levels (there, a command word that cannot be read does not ask); bash's control-character escape is not decoded. When a command also passes text to a shell, heredoc text that no shell reads can disturb the reading of the command words that follow it, and the confirmation for a command word or a command that cannot be read does not apply inside a heredoc body that the shell does not expand, even one read by a shell. The string given to a `-c` option is read the same way when it is written as a single quoted piece without expansion, or with bash's `$'…'` quoting after a shell launcher written by its bare name; written in several pieces, or with a command substitution joined to it, the string is not normalized. Inline interpreter code is checked for a launch of `guard` or of another OpenCode, an OpenCode service command, a call to the OpenCode server API, or a write to OpenCode's configuration or the plugin's settings, only through literal strings and literal paths given to a call it recognizes: a command or a path built by the code or held in a variable of the code is not followed, nor code read from a file or a heredoc. Perl's three-argument `open` and `sysopen` count as writes when their mode writes.
- **Redirections before the program:** a redirection written before the program of a simple command is read as if written behind it by every rule, the limit on the code of a shell apart (see the next point), inside substitutions too: in front of it, glued to the word before it, between its assignments, between a wrapper and what it launches, and anywhere among the words of `xargs` and `find` (`>/tmp/o tee /dev/sda`, `sudo>x ls`, `2>&1 sudo ls`, `env 2>&1 -S'guard off'`, `<$(y) opencode serve`, `<$(y) bash -c 'sudo ls'`, `xargs 2>&1 ssh host`, `find . -exec >x ssh host \;`). An input with blanks or a substitution in its target is also read as standing right behind the name of the program: `<$(y) source x` asks, `source x <$(y)` does not. Whatever its target, a redirection is no word of what `xargs` and `parallel` launch (`xargs sh 2>$LOG` asks as `xargs sh` does). Without a command, `xargs` asks only alone, a redirection counts as a word there (`ls | xargs` asks, `ls | xargs 2>/dev/null` does not), whereas `parallel` asks in both cases. Deeper than 16 substitutions inside each other, or past the limit of this reading, a redirection in the place of a program's word asks, never left to the decision model, even with no program behind it (`>f`); there, text in double quotes that holds an expansion is read as commands, so `echo "a; >x $b"` asks too, and a redirection behind `xargs` is not looked for. Not read that way: a redirection inside the string of `watch` (`watch '>/tmp/o tee /dev/sda'`) or of a here-string (`bash <<<'>x sh $S'`), and one glued behind the program (`rm>x notes`) or glued to a shell that reads a heredoc (`>x bash<<'E'`).
- **Launchers:** the code given to a shell by `-c` (`sh`, `bash`, `dash`, `zsh`, `ksh` and the other shells, with options grouped or separate, `-lc`, `-e -c --`) is read as a command by every rule, under the same settings: where the shell is the program of a command, behind structural words, assignments and the wrappers the rules know (`sudo`, `env`, `timeout`, `xargs`, `watch`…), after `-exec` in `find`, and in a command substitution. The words after the code stay with it (`bash -c 'cp "$1" /tmp/x' _ /etc/hosts` asks). Quoted text stays an argument (`echo 'bash -c "sudo ls"'`). Three shells inside each other are read; deeper, or past the limit of this reading, the command asks, never left to the decision model. The shell runs each code apart, so a code left open (a heredoc, an unclosed quote or substitution, a final `\`) is read on its own and does not hide the next one; at most 32 readings of `-c` code are made for a command as written, all levels together, where the codes that stop cleanly make one reading and each code left open makes one. 32 more go to the texts with a redirection moved behind its program: to the code only they show, and also to a code they spell otherwise, which is read again with all it holds (`bash -c "echo $(<$(z) a); bash -c 'cat <<A0'; …"` reaches that limit with 16 codes left open inside it). Past either limit the command asks in the same way, even for what a refusal would have covered: a code left unread past that limit is not judged, so a rule set to `deny` that only that code would trigger gives this confirmation and not a refusal, including `protected-write` set to `deny`, which holds for any code read within the limit. Every code read counts, so 32 codes left open before a refused code left open too ask instead of refusing, even when one of them stands behind a named descriptor (`bash {fd}>f -c 'cat <<G'`). The two limits are apart, which is where a redirection before the program differs from one behind it: 32 codes left open behind `<$(y)` beside 32 others make 64 readings and ask nothing, whereas with `<$(y)` behind the program all of them fall on the first limit and the command asks. When the code and the command around it each ask with the same force, only the reason found around it is shown (`sh -c 'sudo ls' <<'EOF'` with `rm x` as its body shows the deletion). Not read that way: `eval`, `fish --command`, a shell known only behind a launcher the plugin does not know (`flock`, `chroot`) and `script -c`; a shell behind a long option of a wrapper given its value in the next word (`timeout --kill-after 5 10 bash -c …`, `timeout --signal KILL 10 bash -c …`, `nice --adjustment 5 bash -c …`, while `--kill-after=5` and `-k 5` are read); a shell known only at run time (`$SHELL -c`, `${SHELL} -c`, `$(which bash) -c`), written with braces (`{bash,-c,'…'}`), or behind `builtin command` or `coproc`; a shell inside the string of `watch` (`watch -n 1 "bash -c '…'"`, the same for `watch -n 1 "sudo ls"`); a `-c` in a heredoc read by a shell (`sh <<'EOF'`); a `-c` after a heredoc whose delimiter is quoted only in part (`cat <<E"O"F`, `cat <<E\OF`), since what follows the delimiter is then taken for its body. A heredoc body inside such code is judged with the shell around it, so an ask found there is not left to the decision model as it is for the same heredoc outside a shell (`bash -c 'cat <<EOF` with `rm notes.txt` as its body). Any other command run by another program that takes it in its arguments is examined as a command of its own only by the rules that say so, and only behind the launchers they know; for the other rules, the decision model judges it. `busybox`, `toybox` and `watch` are among the launchers known to the rules that read the program of each command. The string of `env -S`, attached to the option, separate from it, quoted, or given to `--split-string` (abbreviated too), is read as words by the rules, a redirection between `env` and the option included, however the shell's quotes and escapes write the option (`env -""Srm -rf /`, `env --""split-string=rm -rf /`, `env $'\x2dSrm' -rf /`). Two limits to that: an option that only an expansion gives is not read (`env -${X}Srm -rf /`, `env {-Srm,-rf,/}`, `env -S{rm,-rf,/}`), and an `env` in pieces next to a plain `env -S` asks instead of being read (`env -Sls; e""nv -Srm -rf /`). A string the plugin cannot read to its end (quoted at the end of a `-c` string, behind an escaped quote, or past the limit of its reading) and strings nested more than three times ask, never left to the decision model. This reading goes by the text, so a mere mention of `env -S` in free text can ask in the same way, without a decision by the model (`grep 'env -S' x`, `git commit -m "env -S 'x'"`, `git log -S 'env -S x'`, `bash -c 'echo env -S x'`). Self-protection does not need to know the launcher when a command names a protected location: its net asks (see the next point).
- **Words in pieces:** a word is reduced to its value in the words of the command, down to two levels of substitution. Not reduced: the heredoc bodies no shell reads, comments, the code of a non-shell interpreter, a word with a blank or an operator in its value (`"a b".e""nv`), a piece glued to a `$NAME`, and the value of a variable (`f=.e""nv; cat $f`, as with `f=.env`). The file of a script run is looked for by its value (`bash s""cript.sh` reads `script.sh`), in the command itself: not in the code given to a `-c`.
- **Protected write targets:** only the write targets listed under “Protected write locations” count. An output file named by another program's own option or operand, and a target with a blank or an operator in its value, are not recognized as writes; the decision model judges them, unless the self-protection net below asks. **Its net:** a command that does more than read and has OpenCode's configuration or the plugin as a literal word of its own text asks, even in a form of write the plugin does not recognize. The words read are those of the command without its data, the value of a `name=value` word included, whole and from its last `=` (`make DESTDIR=.opencode/x`, `--output=.opencode/a=b`, `D+=x`, `D[0]=x`, `a=b=x`; a location that starts between the two is not read: `x=y=.opencode/a=b`), except `if=` in a segment of `dd`. An assignment alone (`D=x`, `export D=x`, `readonly D=x`) counts only if `$D` or `${D}` appears in the command (`D=.opencode; curl -o $D/x u`); the words in front of a program always count (`CONFIG=opencode.json node x.js`). `echo`, `printf`, `jq`, `test`, `[`, `[[` and `find` without an action that writes or runs are left out when they have no redirection to a file (`2>/dev/null` and `2>&1` do not count), behind the launchers and structural words the net knows, whose own words and values stay read (`nice time -o .opencode/x echo hi`); so are the commands that only read. **Its switch:** none of this is left out, and heredoc bodies are read too, when the whole command relaunches a shell, holds the word `xargs` or `parallel`, pipes into anything but a known reader, gives its output to an interpreter by `>(…)` (`perl`, `python`, `ruby`, `node`, `bun`, `deno`, `php`, `awk`, `gawk`), or sends a group to a file by a redirection right behind it (`{ jq . opencode.json; } >/tmp/x`, `done > x`, not `2>/dev/null`, nor a real redirection behind another one: `{ jq . opencode.json; } 2>&1 >/tmp/x`). **A known reader** receives a pipe without any of this: a program of the plugin's readers (`cat`, `head`, `tail`, `wc`, `grep`, `ls`, `diff`, `rg`, `git show`, `git log`, `git diff`, `tr`, `cut`, `base64`, `sha256sum`…), `sed` with `-n` and `p` or a single substitution without the `e` and `w` flags (`sed s/a/b/`), `sort` and `uniq` without a long option or an output file, or a command left out above, by its bare name or directly under `/usr/bin`, `/bin` or `/usr/local/bin`, without a redirection to a file. Anything else asks, as long as the command names a location: a program the plugin does not know (`| csh`, `| /usr/bin/csh`, `| $SHELL`, `| strace sh`, `| bin/apply`, `| git rm --pathspec-from-file=-`, `| rsync --files-from=- --remove-source-files . /tmp/y`), a shell loop or a group (`| while read f; do curl -o "$f" u; done`, `| { cat; csh; }`), a local program with the name of a reader (`| bin/jq .`), `tee`, `sed -i`, `sed 's/a/b/w x'`, `sort -o`, a second operand of `uniq`. The stages are not followed: only what receives a pipe is looked at. A relaunch is read anywhere in the text, without looking at the stages of a pipeline: a shell, `busybox sh`, `eval`, `source`, `.` as a command, `ssh`, `su`, `watch`, `script`, `flock`, `tmux`, `screen`, `expect`, `chmod +x`, or a program launched by a path that starts with `/`, `./`, `../` or `~/`, outside quotes. A program directly under `/usr/bin`, `/bin` or `/usr/local/bin` is no relaunch for the net (`ls .opencode | /usr/bin/sort`), unless it is itself one of the above (`/bin/sh`); the data of such a program are then not read (`/usr/bin/csh <<'EOF'`, `/usr/bin/python3 -c '…'`). `printf` escapes end a word there (`opencode.json\0`). Past 1,024 distinct path words, the command asks, never left to the decision model. Not recognized either: `.` as a command at the start of a line after another command, or behind `time`, `builtin`, `command -p`, `!`, `if`, `then`, `do`, `else`, `while` or `until` outside a pipe (`ls .opencode; time . /tmp/x`, a pipe into it does ask), and the archive `tar` creates when it is a startup file or under `/etc` (`tar -cf ~/.bashrc .`); the decision model judges them.
  - **What the net does not see** stays with the decision model. A word that reaches a protected location only through a symbolic link: a word is compared as written. A word built by the shell (brace expansion, a variable, a glob, a name joined to a command substitution), a word with a literal prefix and a variable part (`curl -o .opencode/$X`, `for f in .opencode/*.md`), or with the `{}` of `find -exec`, `xargs` or `parallel` (`cp {} .opencode/{}`), while `~/.config/opencode/$X` is recognized. A word with quotes inside it (`.open''code/x`). A value attached to its option (`7z -o.opencode`, `curl -o.opencode/x`, `time -o.opencode/x`; `-Cdir`, `-ddir` and `-Ddir` are read). A word joined by `:` or `,` (`docker run -v .opencode:/c`, `--mount src=…,dst=…`, `--out:.opencode/x`). A value assigned in the command and joined to another one (`a=.open; b=code; curl -o $a$b/x`). An assignment alone that the command does not use as `$D`, even if a program reads it from its environment (`export D=.opencode/x; make install`), without the switch. Without the switch, a location in the data of a non-shell interpreter (`python3 <<EOF`, and inline code, unless a call it recognizes writes there, which excludes Perl's `open` with a `q{…}` mode: see “Command names”), which also keeps `python3 -c 'print("see opencode.json")'` free of a confirmation. The words of a substitution nested in another one, inside a left-out command. A local program with the name of a left-out one, by such a path (`bin/jq opencode.json`): only the last part of its path is compared. An action of `find` built by the shell (`find .opencode $'\x2ddelete'`). A known reader that the command itself replaces by a function, an alias or `PATH` (`cat() { csh; }; echo rm opencode.json | cat`).
  - **What it costs**, as a confirmation for a command that does not write there. A command that only names the location (`git add opencode.json`, `tar -c` of `.opencode`, `CONFIG=opencode.json node x.js`, `D=.opencode; ls $D`). Any read under the switch: a child of `xargs` that only reads (`find .opencode | xargs grep foo`), a read and an unrelated relaunch in one command (`cat opencode.json; ./run.sh`, `chmod +x x`), a heredoc of notes in such a command, a read in a heredoc a shell reads, a pipe into an interpreter that only formats (`cat opencode.json | awk '{print $1}'`, `| python3 -m json.tool`), a pipe into a program that only reads but is no known reader (`| less`, `| column -t`, `| sort --unique`, `| while read f; do echo "$f"; done`), a `|` that is no pipe (`case $x in a|b) echo .opencode/x;; esac`), the mere word `xargs` or `parallel` (`grep xargs opencode.json`), the name of a shell as an argument behind a launcher (`timeout 5 grep sh opencode.json`) or in a quoted pattern (`grep -E 'sh|bash' opencode.json`). A reader outside the plugin's list (`sort`, `cut`, `tree`, `du`, `realpath`, `md5sum`, `less`, `awk`, `python3 -m json.tool`, `tar t`, `cd .opencode && ls`). A reader behind a launcher, unlike a left-out command there (`timeout 5 cat opencode.json`, `nice cat opencode.json`, `time cat opencode.json` ask, `timeout 5 jq . opencode.json` does not). Free text in quotes (`git commit -m "fix opencode.json loading"`, `gh pr create --title "guard.json docs"`). A leading assignment, which can change the program (`LC_ALL=C grep x opencode.json`). An input redirection on a left-out command (`jq . < opencode.json`). A launcher the net does not know, or one of its long options that may take a value (`busybox echo .opencode/x`, `env --ignore-environment echo .opencode/x`). A separator that cuts a left-out command: inside `[[ … ]]` (`[[ -f opencode.json && -d .opencode ]]`), escaped (`echo a \; opencode.json`), or between quotes in a command whose quotes the net does not read, one with a substitution inside double quotes, a heredoc or a comment (`jq "$(x)|.b" opencode.json`); elsewhere a separator between quotes cuts nothing (`jq '.a|.b' opencode.json` and `grep 'a|b' opencode.json || true` do not ask). A comment, in an executed script or not (`npm test # see opencode.json`). In a protected directory, any word with a slash and any program launched by its path (`git add src/x.ts`, `./run.sh`). A call of inline code that reads OpenCode's configuration or the plugin through a copy function (`shutil.copy(".opencode/x", "/tmp/y")`, `copyFileSync`), or that only passes such a path as text to a write call (`f.write(".opencode/x")`). For the other protected locations, under `protected-write`: what the plugin cannot tell from a write by the call's shape (`d.remove("/etc/hosts")`, `copy.copy("/etc/hosts")`), and a write call in a comment of the code. A comparison in an `awk` program with a literal path (`$1 > "/etc/hosts"`). The source of a copy, which counts as a target like its destination (`cp ~/.bashrc /tmp/bak`, `cp -r /etc /tmp/x`). A copy whose source name does not land in the destination (`cp -T /tmp/hooks .git`, `rsync -a /tmp/hooks/ .git`).
  - **Settings.** With `ruleOverrides` setting `self-protection` to `deny`, a command the net asks about is refused, even if it only names the location (`git add opencode.json`), and this refusal replaces another rule's confirmation (`sudo somecmd .opencode/x`).
  - **Other protected locations.** The net covers OpenCode's configuration and the plugin only. For `protected-write` and the device rules these forms stay with the decision model: `patch -r` and `-B`, `patch` and `sponge` on a device, `cpio -p`, `watch` with an option it does not know (`-q 3`, `--int 5`). So do, for `protected-write` alone: a path built by inline code (`Path.home() / ".bashrc"`, `os.path.expanduser("~/.bashrc")`, a path held in a variable), inline code in a heredoc (`python3 <<EOF`), an `awk` file held in a variable (`-v f=~/.bashrc`, `print > f`) or written by a command `awk` pipes into (`print | "tee -a ~/.bashrc"`), a copy into a directory held in a variable (`cp /tmp/fish $DIR`), and an archive or a patch applied in a directory that is not protected itself (`tar -xf /tmp/a -C ~`, `-C .git`, `-C ~/.config`, `tar -C / -xf a`, `unzip /tmp/a -d ~`, `patch -d ~ -p0`, `git -C /etc apply`): what it holds is not read.
- **Copies into a directory:** the destination is read as written, so `cp -r overlay/etc etc` from a project reads `/etc/etc` and asks, as `cp x etc/y` does, while `./etc` does not. The value of an option read as a source (`rsync --exclude hooks /tmp/a .git/`) asks too. Not recognized: a destination in a subshell (`(cp /tmp/hooks .git)`).
- **Inline code that writes:** a literal path is read as a call's first argument or as the destination of a copy. Not recognized: a named argument (`shutil.copy("/tmp/a", dst="/etc/y")`), a receiver held in another name (`f=File; f.write("/etc/y","d")`), a double parenthesis in awk (`print "x" > (("/etc/y"))`).
- **Environment variables that load code:** `shell-startup-file` reads them in front of a program, behind the launchers it knows, and in `export`, `declare` or `typeset` with their value.
  - **Not recognized**, left to the decision model: an assignment followed by `export` without a value (`LD_PRELOAD=x; export LD_PRELOAD`), `builtin export`, `set -a`, `local -x`, `readonly -x`, a quoted name (`export 'LD_PRELOAD'=/x`), a variable in front of `export`, a command run by `xargs` or `find -exec`, or behind a launcher the rule does not know (`chrt`, `taskset`, `flock`, `strace -E`), a body of `case`, a function or `coproc`, a value with a separator in a substitution (`LD_PRELOAD=$(a; b) prog`), an assignment behind a substitution or an escape that holds a blank (`A=$(b c) LD_PRELOAD=/x prog`, `A=b\ c LD_PRELOAD=/x prog`), and a variable already in the environment.
  - **Other variables** are not read, even when they run a program or load code: `MANPAGER`, `GIT_PAGER`, `SUDO_EDITOR`, `LESSOPEN`, `JAVA_TOOL_OPTIONS`, `DYLD_LIBRARY_PATH`.
  - **What it costs:** the rule asks every time for an ordinary form too (`PYTHONPATH=. pytest`, `NODE_OPTIONS=--max-old-space-size=4096 npm run build`, `LD_LIBRARY_PATH=./build ./prog`, `BROWSER=none npm start`, `PAGER=/bin/cat git log`, `EDITOR=nvim git commit`).
  - **The loaded file is not read:** the rule asks about the variable. Neither the rule nor the decision model sees the content of the file it names (`NODE_OPTIONS=--require=/tmp/x.js`).
- **Data read as commands:** where the rules cannot follow the quotes (a heredoc, a `#`, a `$'…'`, a `$(` or `${` between double quotes, anywhere in the command), quoted text is cut like commands. A line or a piece of it that starts with an assignment then asks, as in a commit message written through a heredoc (`git commit -F - <<EOF` with a line `PYTHONPATH=. pytest`), `git commit -m "fix $(date); LD_PRELOAD=/x prog"` or `ls # see; LD_PRELOAD=/x prog`.
- **Cloud credentials:** only the listed files are protected, not their directories. `cp -r ~/.azure /tmp/x`, `tar czf x.tgz ~/.config/gcloud`, `cat ~/.azure/*` and `grep -r token ~/.azure` do not ask, nor does a file outside the list (`~/.azure/TokenCache.dat`). A key in a JSON file is recognized under the exact name `private_key`, as a PEM value, in the first 4 KiB of a file that starts with `{`.
- **Budget of the path check:** a call gets 512 lookups to follow links, 2,048 lookups to find credential files and 128 opened files. Beyond that, the check stops and asks. A relative path costs one link lookup per level of the working directory, and an absolute path at least two. A copy costs at least one more per source whose name can complete a protected location (`hooks`, `fish`, `etc`…), and nothing more for any other source. So a tool that sends 65 single-line strings under a path key gets a confirmation from a directory 7 levels deep, and 257 strings shaped like a path get one from any directory. Under `input`, `output`, `to`, `from` and `target`, only a string without a blank counts: a list of words asks, a batch of texts does not.
- **Persistent git settings:** an alias or a setting that names a program for `git` to run is recognized when given in the command or the environment, not once written to a git configuration file, and git configuration files are not protected locations (git hooks are).
- **Infrastructure commands:** the container and infrastructure rules look for the subcommand right after the tool's name (scaling to zero replicas excepted): with the tool's global options before it, the subcommand is not recognized.
- **Credential files named indirectly:** a credential file is recognized by its path as written; `/etc/shadow`, `/etc/gshadow` and their `-` copies also from the home directory (`~/../../etc/shadow`) and as a relative path with a slash (`./shadow`), resolved from the directories of the call, those of a `cd` included, but not as a bare word (`cd /etc && cat shadow`). Any other file reached relative to a change of directory, and any file reached through a symbolic link or through a value known only when the command runs, is not recognized; written in a form that designates it only once normalized, it may not be recognized. The decision model then judges the command, as it does for a program that prints a credential file's content without naming it (`getent shadow root`).
- **Devices through the file tools:** OpenCode's `write`, `edit` and `patch` tools have no device rule; such a write is left to OpenCode's permissions and the decision model.
- **CodeMode network access:** once you confirm a script that uses `fetch`, or once the decision model allows a script that does not refer to `tools`, what it sends is not checked again: the addresses and the data are computed when the script runs; in OpenCode 2.2 each `fetch` passes through OpenCode's `webfetch` permission, which the plugin does not judge. Such a script can reach any HTTP service that the machine reaches, local services included (among them OpenCode's own local server, which still requires its password), follows redirections, and is not limited in its number of requests; it can also send out what the interpreter offers without any tool, such as the catalogue of tools (names and descriptions) and the machine's clock and time zone. A local or private address is recognized when it is written as is in the code or as the host of an `http(s)` URL, read as the URL parser reads it (`127.1`, `0x7f000001`, `2130706433`); an address built by the code, kept in a variable or resolved by a name is not.
- **Artifact pages:** only the routes of “The server API” (under [Unprotected agent](rules.md#unprotected-agent-unprotectedagent)) are looked for in an artifact's code, written as is or relative with `..`; a route built, encoded (`%`, except `%2e` read as a dot in a `.` or `..` segment of the URL of a form or of a `ping`; HTML entities in its path or its scheme such as `&#106;avascript:` or `java&#9;script:`, JavaScript escapes of its characters such as `\/`, `\\` or `\u002f`, a `data:` URL in base64) or concatenated by the code, kept in a variable, or reached through a `<base>` element is not recognized, and the rest of what a page does once opened (other local services, network requests) is not judged. An artifact provider added by a plugin receives the files and may send them elsewhere; the plugin does not judge where they go.
- **Long inputs:** the decision model receives at most `maxStateChars` characters of the redacted input; beyond that, it judges only the beginning. The local rules see the whole input, except inline interpreter code and quoted text in an `awk` program longer than 64 KiB, which they do not examine: such a command asks for confirmation.
- **Output check:** the decision model may miss a password that reads as an ordinary word, a part where it sees a secret without locating it is masked whole, a large output makes the session wait while every part is checked, and it reads text written by others (a fetched page, a file of a cloned repository) that may be written to make it answer that there is no secret. It adds to the redaction, it never replaces it.
- **OpenCode secrets in outputs:** a credential value or a pairing code printed alone the first time it appears is not recognized, nor is a credential value that does not have the shape of a token (described above), nor a value that is split, partly printed or encoded otherwise than as described under “Other encodings”; a service password shorter than 8 characters is not masked; the environment of the service is masked only for the variables named like a secret, and the metadata of a credential are not masked. The confirmation that these subcommands require remains the main protection.
- **OpenCode subcommands behind another confirmation:** when the same command also matches a confirmation rule checked before them (privilege escalation, an upload, a remote connection), the confirmation shows that rule's reason; the subcommand's reason, with its note on what the output masks, is not shown.
- **`git checkout` with a single argument:** without `--`, `git checkout <name>` switches to a branch or restores a file of that name, depending on what exists in the repository; the local rules leave it to the decision model. A path that starts with `-` is not counted as a file to restore, even after `--`.
- **Other encodings:** only base64 (gzip included) and `xxd`/`hexdump -C` dumps are decoded. `xxd -p` (plain hex), `od`, other compressions inside base64, `rev`, rot13, text split character by character, base64 blocks under 24 characters, without any digit, `+` or `/` (about 0.2% of 30-character blocks), larger than 2 MB, or an output that is exactly a binary `data:` URL still pass. A secret typed by you in the prompt in plain words is masked only by the [prompt check](decision-model.md#prompt-check-promptcheck) of the decision model, and even then a value that reads as an ordinary word without anything around it (`connecte-toi avec admin et soleil`) may pass.
- **Files the plugin cannot read** (`opaque-document`, `opaque-image`):
  - A yes checks nothing. Nothing is masked in a compressed PDF, a `.docx`, a `.xlsx`, an image or a `data:application/pdf` address; in an uncompressed PDF, raw or in base64, and in an uncompressed `.docx`, the text is masked, except a secret cut between two runs of text (`w:t`). The output of `pdftotext` is text: it is masked and checked.
  - OpenCode's `read` goes by the first bytes only (its code was read for version 2.2.5), and these rules by those bytes and by the name: `%PDF-`, PNG, JPEG, GIF and WebP (`RIFF` then `WEBP`), the content before the name, so a PDF named `.png` is a document even with `opaque-image` off. The check reads at most the first 4 KiB of a regular file, like the check of private keys, with the same risk: a path on a file system that does not respond blocks the call. Beyond its limits the name alone counts, and a text file named `.pdf` still asks for nothing to protect.
  - The shell rules go by the name only: `cat notes.txt` of a renamed PDF does not ask.
  - An MCP or plugin tool does not ask: `mcp_fs_read_file` on a `.pdf` is not a read for these rules.
  - A file attached to the prompt is not a tool call: no rule asks, and redaction has the limits above.
  - A scanned page is an image: no text to mask, in the file or in the output of `pdftotext`; only the model, if it reads images, sees what it says.
  - An extraction in two steps (`pdfimages`, or `unzip` on a `.docx`, then a read of the `.png`) asks at the second step only while `opaque-image` is on.
  - The readers are a closed list: `less`, `tac`, `dd`, `sed`, `tr`, `git show HEAD:a.pdf`, an interpreter, or a file named by a variable (`cat "$f"`), `xargs` or `find -exec` do not ask, nor does a file opened apart (`exec 3< a.pdf`) or read by the shell line by line (`mapfile`, `while read`).
  - A quoted text or a heredoc is read as commands in the statement that launches a shell or a program, not in the others: `echo 'cat a.pdf' > x.sh; sh x.sh` in one command does not ask (written then run in two calls, the [script tracking](decision-model.md#decision-model) reads it), nor does `X='cat a.pdf'; echo "$X" | sh`, or `printf 'cat a.pdf\n' | sh`. A statement that launches a program by its path reads its own quoted text as commands: `./x.sh 'cat a.pdf'` and `/usr/bin/git commit -m 'cat a.pdf'` ask, and so does a group, a loop, a branch of an `if` or a function that holds a launch.
- **Download then run in two steps:** `curl -o x.sh …; sh x.sh` is not a pipe; the second command is judged by the decision model.
- **Scripts written then run:** the content is checked only for files created in full by the agent in the session (see [Scripts written then run](decision-model.md#decision-model)); the decision model sees it only if it already judged it in full, and only its first `maxStateChars` characters. A script not read by a shell that the model does not see whole (not shown, cut, or no model consulted) is read only for the forms of inline interpreter code: a literal path written to a protected location, a literal launch of `guard` or OpenCode, a dangerous command in a file that holds an execution function, wherever the function is. Dangerous code in another form is not seen by the local rules: a path or command built at run time, a path held in a variable, a write mode given by name (`mode="a"`, or `open(file=…)`), code in an imported module, network access. That reading can also ask for nothing dangerous: the end of a command runs across lines (`git reset HEAD` then `"--hard"` further on), and the word `guard` or `opencode.json` next to an execution function is enough, even in a text that launches nothing. Not concerned: a copy of the file, a file run after another `cd`, through a variable, by a program that is not recognized (`make`, `npm run`…), or run inside `sh -c "…"` (`sh -c "./x"`, `sh -c "bash f.sh"`). For such files the command is judged on its own text. The tracking lives in memory: it starts again from zero when OpenCode restarts or reloads the plugin, which it does once a project has had no session activity for a while (60 minutes by default, OpenCode's `experimental.location_idle_timeout` setting, which a project's configuration can lower; see [Full protection](configuration.md#protecting-the-plugin-from-project-configuration)); a file written before is then judged like a file the agent did not create. The tracking keeps up to 200 files per session and 1,000 sessions; beyond, the oldest file is forgotten and judged the same way. The decision model state then holds up to the input plus one `maxStateChars` per script (at most 4).
- **Private keys recognized by their content:** only a path written in the command or the tool input counts (a program that opens a key by itself is not seen), within the per-check limits (beyond them, a confirmation is asked), with the header in the first 4 KiB. The headers are read in a synchronous hook without a timeout: a path on a network or automounted filesystem that does not respond blocks the call.
- **Protected writes through links:** links are resolved when the call is checked, in a synchronous hook without a timeout (a path on a filesystem that does not respond blocks the call). Not recognized: a link created or changed by the same command or after the check, a hard link, a bind mount, a write through an open file descriptor, and a link whose name is the protected location (a `.opencode` that points elsewhere: only its name is protected, not the directory behind it; the plugin directory and OpenCode's global configuration directory are protected under both forms). The decision model still judges these writes.
- **Devices named indirectly:** a redirection to a target whose value is only known when the command runs (`> "$OUT"`, common in scripts) is left to the decision model. Symbolic links are not resolved for the targets of `dd` and `shred` by the device rules (`protected-write` and `self-protection` do resolve those of `dd`), for a destination given as `--target-directory=…`, nor for a target found only in code or data for another program, and the read-write redirection (`<>`) is recognized only with the device written as is. Link resolution has the limits described for protected writes: at most 512 path components looked up per check and 40 links per path (beyond them, a confirmation), the state of the disk when the call is checked, and no write through an open file descriptor (`/proc/self/fd/…`, `/dev/fd/…`) or through a link created by the same command. A link that leads to `/proc/self/cwd` or `/proc/thread-self/cwd` is recognized as such only when at least two directories stand for it, counting the command's directories and the OpenCode server's directory.
- **Relative paths given to an MCP server:** the plugin resolves them from the session directory. A local MCP server started in its own configured directory (`cwd` in its configuration) resolves them from that directory instead, so a relative path that reaches a protected location only from there is not recognized.
- **Relative writes after a change of directory:** a chain of relative `cd` is not followed (each literal target is resolved from the directory where the command starts), and a directory given through a variable is not resolved; the session directory and the `workdir` still apply.
- **Pattern bounds:** not recognized: a secret name with more than 128 characters after its last secret word, a URL scheme longer than 64 characters. A JWT whose header contains `-eyJ` is redacted from that point on (the header holds no secret), and not at all if fewer than 10 characters separate that point from the next `.`. A PEM block whose body contains another `-----BEGIN` is judged block by block; a truncated block is still redacted by the "header followed by base64 lines" pattern (lines of 16 characters or more). In what follows a value cut short, the value of a neighbour ends at any `<` (`password=…,token=parseToken2<Claims>(raw)`: `parseToken2` goes).
- **Options and keys:** not redacted: options with a single dash (`openssl -pass`, `-passin`, `mysql -p…`, `sshpass -p`) and quoted passphrases after a lowercase key (`password: "two words"`). Redacted although not secret: a value that names a variable, after a key that contains a secret word (`…_PASSPHRASE_ENV_NAME = "…"`).
- **XML and HTML:** not redacted: a value of several words in an element; a value containing `<` or `>`, in a CDATA section as well (`<password><![CDATA[a<b>c1]]></password>`); an element or a tag beyond the bounds (2,048 characters for the value, 8,192 for the attributes before it, 18,432 for a whole tag); an attribute without quotes (`<add key=password value=…/>`); another attribute than `value` (`<meta name="api-token" content="…"/>`); a `>` in an attribute placed before (`<add description="a>b" key="password" value="…"/>`, `<password a=">">…</password>`); a comment in the element (`<password><!-- c -->…</password>`); `<input type="password" value="…">`, whose `type` does not count; an escaped form (`&lt;password&gt;`); in a JSON text, a CDATA section or an attribute separated by a literal `\n` (`"<password>\n  <![CDATA[…]]>\n</password>"`); an identifier followed by a tag outside [the closed list](rules.md#secret-redaction), or with attributes (`password=abc123def<section>`, `token=abc123def456<td class="a">`), which reads like a generic call; a value holding a `<` that no letter follows (`password=Abcd-1234<5x`), or a non-ASCII character before a tag that is not a closing one (`password=Motdepassé1<td>`); the end of a value after a `<` that does not follow an identifier (`password=Abcd-1234<xyz!`: only `Abcd-1234` goes); after a private or ssh key name, a base64 value that starts with `/` and has neither `+` nor `=`, read as a path; the value of an attribute whose name ends in a descriptive word, a real secret included (`PasswordHash`, `password_confirmation`). Redacted although not secrets: an assignment-shaped text glued to a closing tag, like the same text without a tag (`<span>androidx.credentials.registry:provider-events2</span>`); the `value` of a form field or a component named with a word (`<input type="submit" name="password" value="Login123"/>`, `<Tabs.Trigger id="token" value="tokens12">`); an example that passes the checks of `password=` (`<token>Word2Vec</token>`, `<token>abc123xyz</token>`, `<password>test1234</password>`). `guard redaction off markup_secret` does not touch a value glued to a tag, which belongs to `generic_secret`.
- **Names and forms of secrets not covered:**
  - **Names:** not redacted: `pass` glued to a word (`dbPass`, `smtpPass`, `keystorePass`). Redacted although not secrets: a name with a secret word that describes something else, outside XML (`tokenUrl`, `token_endpoint`, `secretName`).
  - **Name and value apart, in YAML and JSON:** not redacted: `- name: DB_PASSWORD` then `value: …` (Kubernetes), `{"name":"DB_PASSWORD","value":"…"}` (ECS), `{"key":"api_token","value":"…"}` (Postman).
  - **XML forms outside the lists:** not redacted: `<string name="api_key">…</string>`, `<init-param>` with `<param-name>` and `<param-value>`, `<property name="password"><value>…</value></property>`.
  - **Passwords with `()[]{}<>`:** a generated value that holds one of these characters is read as code and not redacted (`DB_PASSWORD=aB3(xY9]kLmN2pQ`).
- **A value redacted by mistake:** the agent reads the marker instead of the value. An `edit`, `write` or `patch` that copies the marker is refused by the `placeholder` rule ("writing it would destroy the real secret. Make a targeted edit that does not include the placeholder"), so rewriting a whole file that holds one is refused too; an edit of another part of the file passes. The arguments of an MCP tool, the code of `execute`, a `websearch` and a `webfetch` that hold a recognized value are refused (`secret-network`), a value recognized by mistake as well; add it to `allowlist`, or turn the rule off with `guard rules off secret-network`. The content written by the native `write` and `edit` is not checked for secrets.
- **Delegated to the decision model:** `npx`, `bunx`, `yarn dlx`, `uv run` and similar commands run arbitrary packages; a local rule would be too noisy (`npx tsc`…), so they are judged by the model.
- **Windows:** not tested: the tests run on Linux and macOS, and hundreds of them fail on Windows, not all of them looked into. The usual forms were seen to behave as on Linux (`.env`, `~/.ssh`, `.opencode`, `C:\Users\…\.ssh\id_rsa`, `rm -rf`, `sudo`), but a relative path with backslashes (`.opencode\x`, `.git\hooks\pre-commit`) is not recognized by the local rules, so it is left to the decision model, and without the model it passes.
- **Letter case:** protected paths, credential names and the `guard` command are compared case-sensitively, as on Linux. On a file system that ignores case (the default on Windows and macOS), another spelling of the same file (`.OPENCODE`, `OpenCode.json`, `.ENV`) is not recognized by the local rules. Unicode forms (NFC, NFD on macOS) are compared as written too.
- **Very long commands:** no limit of size or time cuts the analysis of a shell command. Its cost grows with the length, and a crafted command of a few hundred kilobytes takes tens of seconds, during which the server is busy for every session. OpenCode waits for the verdict: nothing runs unchecked in the meantime.
- **Download then run in one command:** no local rule links `curl … -o f` to a later `sh f` in the same command, so it is left to the decision model. Without the model, it passes.
- **Environment secrets** are read once, when the plugin starts: after rotating a secret, restart OpenCode.
- **Project configuration and project plugins:** a repository's `opencode.json` can remove the plugin (`"-guard"`, `"-*"`) or replace its options (a relaxation among them, such as a [feature option](configuration.md#turning-features-off) at `false`, counts only if your global sources declare it), unless a configuration layer loaded after the projects declares it; a global policy only prevents blocking it by policy (see [Protecting the plugin from project configuration](configuration.md#protecting-the-plugin-from-project-configuration)). In every case, a repository that ships its own plugin runs code when OpenCode opens it.
- **A project's `secretPatterns`:** they are added to yours and redact what the decision model reads, so a broad pattern can hide a call from it. A project with such a pattern loses the model's grants of confirmations, but a call no rule matches is still judged on the redacted text. This opens nothing new: a project can remove the plugin altogether (see above).
- **Wire safety net:** only JSON bodies (plain, gzip, zstd, br or deflate) and JSON WebSocket frames are redacted; model requests are JSON. A body or a frame that is not, or that cannot be decoded, is sent unchanged (reported once in the log). A request whose redaction fails is blocked, and blocks the session until the content that causes it is gone. Not verified: if a provider signs the request body (AWS SigV4 on Bedrock) before the hook, a redaction on the wire would invalidate the signature and the request would fail, without leaking the secret.

**Notes.**
- **Hot reload.** OpenCode watches the plugin files and reloads the plugin on every change, including in running sessions. Edit a copy and deploy the files in one go, or stop the service while editing. When you use OpenCode itself to edit the plugin, the self-protection asks for confirmation on every write.
- **Imports.** Only `import type` is used from `@opencode/plugin`: Node refuses to strip types from `.ts` files under `node_modules`, and OpenCode provides the package at runtime anyway.
- **Credits.** The secret patterns are adapted from OpenCode's `packages/http-recorder/src/redaction/secrets.ts` (MIT, © 2025 opencode). The list of other coding agents' credential files and the backup suffixes are adapted from [cc-safety-net](https://github.com/kenryu42/cc-safety-net) 2.6.12 (`src/core/rules/secret.ts`, MIT, © 2026 J Liew), and some test cases come from its `tests/fixtures/gate/harvested-verdicts.jsonl`, with this plugin's own expected verdicts.
